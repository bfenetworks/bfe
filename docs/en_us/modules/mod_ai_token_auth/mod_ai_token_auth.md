# mod_ai_token_auth

## Module Overview

mod_ai_token_auth supports API-key (token) authentication for LLM services. An API-key represents a token with certain access permissions and quotas for specific LLM services. This module checks the API-key carried in the request according to rules to determine whether the request is allowed to access the LLM service.

Request header carries the API-key:
```
Authorization: Bearer <api-key>
```

## Core Concepts

### Token

Token is the runtime api-key object used by the module in memory, converted from the `Tokens` section of the configuration file. A Token contains:

- `Key`: the api-key string
- `Status`: api-key status
- `Name`: display name
- `ExpiredTime`: expiration time; `-1` means never expires
- `UnlimitedQuota`: whether the quota is unlimited
- `Models` / `BlockModels`: allowed / blocked model list
- `Subnet`: allowed source IP subnet list
- `Tags`: api-key tags for logging or extension
- `QuotaPlans`: associated quota plan list

### Token Status

| Value | Constant | Meaning |
| ----- | -------- | ------- |
| 1 | `TokenStatusEnabled` | Enabled |
| 2 | `TokenStatusDisabled` | Disabled |
| 3 | `TokenStatusExpired` | Expired |
| 4 | `TokenStatusExhausted` | Quota exhausted |

`TokenStatusExhausted` is mainly generated by external systems or configuration and is used by the module mainly for logging/monitoring; the actual request phase still checks the quota balance in Redis in real time.

### QuotaPlan

A quota plan describes the token quota available to an api-key. The runtime structure is as follows:

| Field | Meaning |
| ----- | ------- |
| `Id` | Quota plan ID |
| `Unlimited` | Whether the quota is unlimited. When `true`, Redis is not read and requests are always allowed |
| `PassNoQuota` | Whether to allow requests when quota is insufficient. When `true`, requests are allowed even if the balance is 0 |
| `RedisKey` | The Redis key that stores the quota balance |
| `CreateTime` | Creation time |
| `ExpiredTime` | Expiration time; `-1` means never expires |
| `Quota` | Total quota, in tokens |
| `ResetMode` | `0` non-periodic; `1` periodic quota package |

> Note: the difference between `Unlimited` and `PassNoQuota`:
> - `Unlimited=true`: no quota limit, Redis is not read, requests always have quota.
> - `PassNoQuota=true`: still reads balance from Redis and deducts, but does not reject requests when balance is 0.

## Working Principle

### Token Authentication Flow

1. **Request Entry**: When a request arrives, the module checks if it matches the authentication rule
2. **Token Validation**: Extracts the API-key from the `Authorization` header of the request and validates its validity (status, expiration time, etc.)
3. **Model Permission Check**: Verifies whether the requested model is in the allowed list and not in the blocked list
4. **IP Subnet Check**: Verifies whether the request source IP is within the allowed subnet range
5. **Quota Check**: Checks if the associated quota plans have sufficient quota
6. **Quota Deduction**: After the request completes, extracts the token usage from the response body and deducts the corresponding quota

### Quota Check (HasBalance)

For each non-unlimited quota plan, the module calls `QuotaPlan.HasBalance` during the request phase:

1. If `Unlimited=true`, return sufficient quota directly.
2. If `RedisKey` is empty, return an error.
3. Read the balance via Redis `GET`:
   - If the key does not exist (Redis returns `nil`), treat it as first use and process it as full `Quota`.
   - If read succeeds, quota is sufficient when balance `> 0`, otherwise insufficient.
   - If other Redis errors occur, return `INTERNAL_QUOTA_ERROR`.

### Quota Deduction (Deduct)

After the request returns successfully, the module calls `QuotaPlan.Deduct` based on the token usage in the response:

1. If `Unlimited=true` or deduction amount `<= 0`, return directly.
2. If `RedisKey` is empty, return an error.
3. Execute atomically via Lua script:
   - If the Redis key does not exist, initialize it to `Quota` first.
   - Deduct `min(current balance, usage)` from the current balance.
   - Return the remaining quota after deduction.

The Lua script logic is approximately as follows:

```lua
local raw = redis.call('GET', KEYS[1])
local current
if raw == false then
    current = tonumber(ARGV[2])
    redis.call('SET', KEYS[1], current)
else
    current = tonumber(raw)
end
local amount = tonumber(ARGV[1])
local deduct = math.min(current, amount)
if deduct > 0 then
    redis.call('DECRBY', KEYS[1], deduct)
end
return math.max(0, current - deduct)
```

### Redis Key Initialization

The quota balance key is written to Redis by external systems (such as ai-gateway-api) when the quota is created or reset. If the following situations occur, BFE will handle them gracefully:

- During the request phase, if the key does not exist: `HasBalance` treats it as full quota and allows the request.
- During the deduction phase, if the key does not exist: `Deduct` first initializes the key to `Quota`, then deducts.

This avoids `INTERNAL_QUOTA_ERROR` caused by the Redis key not being initialized in time.

### Error Codes

The module may return the following quota-related errors:

| Error Code | HTTP Status | Meaning |
| ---------- | ----------- | ------- |
| `INTERNAL_QUOTA_ERROR` | 500 | Non-nil error occurred while reading Redis quota |
| `QUOTA_EXHAUSTED` | 429 | Insufficient quota balance |
| `QUOTA_EXPIRED` | 429 | Quota plan has expired |

Other common error codes are defined in `bfe_basic/request_ai_basic.go`.

## Relationship with mod_ai_route

- `mod_ai_token_auth` is responsible for api-key authentication, model permissions, subnet, and quota.
- `mod_ai_route` is responsible for forwarding the request to the target cluster and model according to AI routing rules after authentication.
- The two modules work together through BFE's module execution order; usually `mod_ai_token_auth` executes before `mod_ai_route`.
