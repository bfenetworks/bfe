# SC42 expr 条件引擎三模式

## 1. 场景背景与目的

BFE 条件引擎一期引入基于 expr-lang/expr 的新表达式引擎，与旧条件引擎双轨并存，
由 `bfe.conf` 的 `Server.ConditionEngineMode` 选择模式（进程级，BFE 启动时设置）：

- **LegacyFirst（默认）**：旧引擎优先，语义与旧版完全一致；旧引擎编译失败（如混写新风格表达式）
  时回退新引擎；双失败 → 配置加载报错；
- **ExprCompatible**：新引擎编译 + 旧原语兼容层（`legacyPatcher` 把旧原语名重写为 Env 方法），
  新旧写法可混用；编译失败不回退，直接报错；
- **ExprOnly**：纯新表达式，旧原语名即未知函数；编译失败不回退，直接报错。

模式配置兼容字符串（大小写不敏感）与数字写法（`0`/`1`/`2`），非法值启动 fail-fast。

本场景验证三模式在**真实 BFE 进程**中作为路由条件消费点（`route_rule.data` 的 `Cond`，
经 `condition.Build` 分派）的实际行为：

- **ExprOnly**：新风格表达式（`ReqMethod() in ["GET"] && ReqPath() startsWith "/api"`）命中与未命中回落；
- **ExprCompatible**：旧原语可用、新旧混写可用；
- **LegacyFirst**：旧条件回归基线不变；新风格表达式触发回退并成功编译；
- **fail-fast**：非法模式值、ExprOnly 下的旧原语、表达式类型错误均导致 BFE 启动失败；
- **数字写法兼容**：`ConditionEngineMode = 0/1/2` 与字符串模式行为一致。

条件求值结果通过路由命中哪个 cluster 直接判定：mock 后端响应体含 cluster 名，
命中 `cluster_expr_hit` 即条件为真，回落 `cluster_expr_default` 即条件为假（或前序规则不命中）。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程（每个测试例独立临时目录与随机端口）。
- `ConditionEngineMode` 是进程级设置（BFE `StartUp` 起始处一次性设置，先于路由表加载），
  不可热改——**切换模式必须重启 BFE 进程**，因此每个测试例（或子用例）独立启动 BFE 实例。
- 不涉及 AI 网关与 `conf-agent`。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | `Server.ConditionEngineMode`（由测试经 `common.RewriteConfLine` 改写；缺省不写即为默认 LegacyFirst） |
| `server_data_conf/host_rule.data` | 声明产品线对应的 Host（`expr.example.org` 等，见 §4.3） |
| `server_data_conf/route_rule.data` | `ProductRule` 高级路由规则，`Cond` 字段为各用例的条件表达式（条件引擎消费点） |
| `cluster_conf/cluster_conf.data` | 各 cluster 的基础配置 |
| `cluster_conf/gslb.data` | GSLB 子集群权重配置 |
| `cluster_conf/cluster_table.data` | 运行时根据 mock 后端地址动态生成 |

## 4. 路由表设计

### 4.1 route_rule.data 模板

每个测试例按自身模式与条件生成 `route_rule.data`，结构如下（`Cond` 为各用例的条件）：

```json
{
    "Version": "20261030000000",
    "ProductRule": {
        "expr_product": [
            { "ClusterName": "cluster_expr_hit",     "Cond": "<用例条件表达式>" },
            { "ClusterName": "cluster_expr_default", "Cond": "default_t()" }
        ]
    }
}
```

规则按顺序匹配，命中即返回：条件为真 → `cluster_expr_hit`；条件为假或编译期不命中
（运行期求值错误按 false 处理）→ 回落到 `default_t()` 规则 → `cluster_expr_default`。

> ExprOnly 子用例的回落规则用 expr 原生常量 `true` 代替 `default_t()`（ExprOnly
> 按设计拒绝旧原语名）；`true` 在三种模式下均可编译。

### 4.2 cluster 与 mock 后端

| cluster | mock 后端行为 |
|---------|---------------|
| `cluster_expr_hit` | 返回 200，响应体含 `cluster_expr_hit` |
| `cluster_expr_default` | 返回 200，响应体含 `cluster_expr_default` |

### 4.3 host_rule.data

按用例需要声明 Host 到产品线的映射（单 Host 用例用 `expr.example.org`，
LegacyFirst 双规则用例额外使用 `legacy.example.org` / `fallback.example.org` 映射到
独立产品线，避免规则间相互影响）：

```json
{
    "Version": "20261030000000",
    "Hosts": {
        "expr_product": ["expr.example.org"],
        "legacy_product": ["legacy.example.org"],
        "fallback_product": ["fallback.example.org"]
    },
    "HostTags": {
        "expr_product": ["expr_product"],
        "legacy_product": ["legacy_product"],
        "fallback_product": ["fallback_product"]
    }
}
```

### 4.4 bfe.conf 模式改写

各用例启动 BFE 前调用 `common.RewriteConfLine(confDir/bfe.conf, "ConditionEngineMode", "<值>")`
写入模式（SC40 改写 `EnableAiGateway` 的同一机制）；不写该键的用例验证默认模式行为。

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | ExprOnly 纯表达式路由与回落 | `ConditionEngineMode=ExprOnly` 下新风格表达式 `ReqMethod() in [...] && ReqPath() startsWith ...` 命中 `cluster_expr_hit`；方法不在集合内/路径不前缀匹配时回落 `cluster_expr_default` |
| TC-02 | ExprCompatible 旧原语混写兼容 | `ConditionEngineMode=ExprCompatible` 下旧原语 `req_host_in(...) && req_path_prefix_in(...)` 可用；新旧混写 `req_path_prefix_in(...) && ReqHeader(...) == "on"` 可用；header 不满足时回落 |
| TC-03 | LegacyFirst 默认基线与回退 | 不写 `ConditionEngineMode`（默认 LegacyFirst）：旧原语条件回归基线不变；新风格表达式条件（旧引擎编译失败）回退 expr 引擎编译成功并按表达式语义路由 |
| TC-04 | 非法模式与非法条件启动失败 | (a) `ConditionEngineMode=Bogus` 启动失败；(b) `ExprOnly` + 旧原语条件启动失败（unknown name）；(c) `ExprOnly` + 类型错误表达式 `ReqMethod() && true` 启动失败 |
| TC-05 | 数字写法与大小写兼容 | `ConditionEngineMode=2` 等同 ExprOnly（新表达式路由成功）；`=1` 等同 ExprCompatible（旧原语可用）；`=0` 等同 LegacyFirst（旧原语基线）；小写 `exprcompatible` 亦可解析 |

优先级：TC-01/02/03 为 P0，TC-04 为 P1，TC-05 为 P1。

## 6. 与其他场景的依赖关系

- 条件消费点（`route_rule.data` 的 `Cond` → `condition.Build`）与 SC01 等场景相同，
  但本场景使用独立的 Host、产品线与 cluster，互不影响；
- `ConditionEngineMode` 改写机制复用 SC40 的 `common.RewriteConfLine` 先例；
- 不依赖其它场景，可独立运行。
