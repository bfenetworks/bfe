# SC25 缓存查找前移

## 1. 场景背景与目的

`mod_ai_cache` 的缓存查找回调从 `HandleAfterLocation` 前移到 `HandleFoundProduct`，
模块注册在 `mod_ai_token_auth` 之后、`mod_ai_route` 之前（修改说明见
`docs/zh_cn/modifications/2026-10-02-ai-cache-lookup-before-route/design-changes.md`）。
核心收益是**懒解析下沉**：意图分类由路由条件原语 `req_ai_intent_in(...)` 在
`mod_ai_route` 规则求值时按需触发（懒解析），缓存查找前移后，命中请求在路由
求值之前短路，**不再触发决策服务调用**（此前命中请求白付一次分类延迟）。

本场景是首个 `mod_ai_cache` + `mod_ai_intent` 同时加载的组合场景，验证：

- 命中请求决策服务零新增调用、上游零新增调用（TC-01，核心收益）；
- 未命中路径的路由语义与懒解析时机不变（TC-02）；
- 命中请求的访问日志口径：`ai_cache_status=hit` 且 `ai_route_rule_hits` /
  `ai_target_model` / `ai_intent_*` 为空，未命中请求则正常（TC-03，下游报表适配依据）；
- `x-bfe-skip-ai-cache: on` 跳过头在新位置下仍走完整链路（TC-04）；
- 缓存规则 Cond 引用 `req_ai_intent_in` 时宽容加载（WARN 不拒绝，TC-05）；
- 缓存查找绝不先于鉴权：未鉴权请求拿不到缓存答案（TC-06）。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程 + 嵌入式 Redis（`common/redis_server.go`）
  + **mock 决策服务**（测试进程内 `httptest.Server`，SC22 同款模式精简版，
  按 last user message 关键词脚本化返回 System One JSON，提供调用计数）。
- mock 上游两个：`cluster_flash` / `cluster_kimi`（答案 content 带 cluster 标识）。
- 不涉及 `ai-gateway-api` 与 `conf-agent`。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 `EnableAiGateway`，加载 `mod_ai_token_auth`、`mod_ai_cache`、`mod_ai_route`、`mod_ai_intent`、`mod_access_pb3` |
| `mod_ai_route/mod_ai_route.conf` | 指定 `ai_route.data` 路径 |
| `mod_ai_route/ai_route.data` | 定义 apikey 级路由规则（含 `req_ai_intent_in` 条件，懒解析触发源） |
| `mod_ai_intent/mod_ai_intent.conf` | 决策服务地址（运行时写入 mock 地址）、超时与缓存参数（测试值见 §4.4） |
| `mod_ai_intent/intent_questions.data` | 问题集（task_type 单问题即可） |
| `mod_ai_cache/mod_ai_cache.conf` | 指定缓存规则路径与 Redis 连接参数 |

| `mod_access_pb3/mod_access_pb3.conf` | 访问日志（b2log）输出目录，TC-03 解析日志字段用 |

> 便于按 TC 覆盖规则条件；Redis 连接通过 `rewriteModBns` 将模板中的 BNS 名映射
> 到嵌入式 Redis 地址。

## 4. 测试 Cluster 与关键配置

### 4.1 cluster_flash / cluster_kimi

两个 mock 上游后端（`common/mock_backend.go`），各返回 200 与固定答案体，
答案 content 带 cluster 标识（`from cluster_flash` / `from cluster_kimi`），
响应含 `usage`。`Hits()` 统计命中次数——"请求落到哪个 cluster"由哪个后端的
`Hits()` 断言。

### 4.2 mock 决策服务

测试进程内 `httptest.Server`，实现 System One 协议 `POST /v1/systemone`，
响应脚本（按 `state` 即 last user message 关键词匹配）：

| prompt 关键词 | 响应脚本 |
|---------------|----------|
| 「单元测试」 | `task_type.choice=test_writing`、`answer_confidence=0.93` |
| 「写文档」 | `task_type.choice=doc_writing`、`answer_confidence=0.90` |
| 其他 | `task_type.choice=coding`、`answer_confidence=0.90`（默认脚本） |

- **观测手段**：`Calls()` 记录决策服务被调用次数（每次测试前置清零）——
  **本场景核心断言对象**；
- 本场景不涉及熔断/故障用例，`mod_ai_intent.conf` 用默认熔断参数即可，
  `TimeoutMs` 测试值设为 **2000**（本机 CPU 版决策后端延迟高）。

### 4.3 路由表设计

#### apikey_ak_front（全部 TC 使用）

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| intent-flash | `req_ai_intent_in("task_type", "test_writing", 0.9)` | `cluster_flash` | 无 |
| intent-default | `default_t()` | `cluster_kimi` | 无 |

> 说明：规则 1 引用意图原语——**这是懒解析的触发源**；缓存命中短路在其求值
> 之前发生，是 TC-01 零调用断言的依据。`doc_writing`/`coding` 无专属规则，
> 走 `intent-default` 到 `cluster_kimi`。

#### ApikeyRouteTableBindings

```json
{
    "ak_front": ["apikey_ak_front"]
}
```

### 4.4 模块配置

`mod_ai_intent.conf` 测试值：

```ini
[basic]
DecisionServiceAddr = http://127.0.0.1:<决策服务端口>   # 测试运行时写入 mock 决策服务地址
QuestionsPath = mod_ai_intent/intent_questions.data
TimeoutMs = 2000
MaxStateChars = 2000
CacheSize = 10000
CacheTTLSeconds = 1800
ExplicitIntentHeader = X-AI-Intent

[log]
OpenDebug = false
```

`intent_questions.data`（单问题即可满足本场景）：

```json
{
  "Version": "2026100201",
  "MinConfidence": 0.6,
  "Questions": [
    {
      "Name": "task_type",
      "Type": "choice",
      "Instructions": "这条请求属于哪类研发任务？",
      "Criteria": {
        "coding": "编写或修改代码、调试、重构",
        "test_writing": "编写测试用例、单元测试、集成测试",
        "doc_writing": "编写文档、README、注释、接口说明"
      }
    }
  ]
}
```

缓存规则（TC-01~TC-04、TC-06；`cond` 不引用意图原语——缓存决策不依赖意图）：

```json
{
    "cond": "default_t()",
    "cacheKeyStrategy": "lastQuestion",
    "cacheTTL": 3600,
    "maxBodyBytes": 1048576,
    "maxValueBytes": 1048576
}
```

TC-05 的缓存规则 `cond` 为 `req_ai_intent_in("task_type", "doc_writing") &&
default_t()`（验证宽容加载）。

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 命中请求零决策服务调用 | 同一问题请求 2 次：第 1 次 miss（决策服务 +1、flash +1）；第 2 次 hit——决策服务**不增**、flash **不增**、`X-Bfe-Ai-Cache: hit`（懒解析下沉核心证据） |
| TC-02 | 未命中路径意图路由不变 | 两个不同问题各请求 1 次（互不命中缓存）→ 决策服务 +2；「单元测试」→ flash，「写文档」→ kimi；证明前移未破坏 miss 路径的路由语义 |
| TC-03 | 命中请求日志口径 | b2log 解析：hit 请求 `ai_cache_status=hit` 且 `ai_route_rule_hits`/`ai_target_model`/`ai_intent_*` 为空；miss 请求三者正常非空 |
| TC-04 | 跳过头走完整链路 | 已缓存问题 + `x-bfe-skip-ai-cache: on` → 无 hit 响应头，决策服务 +1、后端 +1，按意图路由（skip 在新位置下语义不变） |
| TC-05 | 含意图条件的缓存规则宽容加载 | 缓存规则 Cond 含 `req_ai_intent_in` → BFE 正常启动、规则生效（miss→hit 正常）；WARN 日志人工核对（单测已锁告警代码路径） |
| TC-06 | 未鉴权请求不返回缓存 | 无 Authorization 请求已缓存问题 → 401，不返回缓存答案；后端/决策服务均不增（缓存查找在鉴权之后） |

## 6. 公共基础设施

本场景复用既有框架能力：

1. **`common/redis_server.go`**：嵌入式 Redis，`mod_ai_cache` 连接（缓存回写异步，
   通过轮询 Redis 键消除竞态，最长 5s，沿用 SC20 模式）。
2. **`common/bfe_config_builder.go`**：运行时生成 `ai_route.data` /
   `mod_ai_cache_rule.data`；`rewriteModBns` 将 BNS 映射到嵌入式 Redis。
3. **`common/mock_backend.go`**：`cluster_flash` / `cluster_kimi`，`Hits()` 计数与
   cluster 标识答案。
4. **mock 决策服务（本场景新增精简版 helper）**：SC22 决策服务 mock 的裁剪版
   （单问题、3 条脚本、计数器、无故障开关/热更逻辑）。
5. **b2log 访问日志解析（TC-03）**：复用 SC22 TC-13 的 `accessLogs()` helper 模式，
   断言 `ai_cache_status` / `ai_route_rule_hits` / `ai_target_model` / `ai_intent_*`。

> 说明：每个测试例拥有独立临时工作目录、独立 BFE 实例与独立 mock 计数，
> 用例间无状态泄漏。

## 7. 与其他场景的依赖关系

- 依赖 SC01（路由表查找与绑定）、SC02（多 API-Key 基础能力）；
- 复用 SC20 的缓存基建（嵌入式 Redis、缓存规则生成、回写轮询断言模式）；
- 复用 SC22 的 mock 决策服务模式、`ai_intent_*` 日志断言模式与
  `TimeoutMs=2000` 测试参数；
- 本场景上线后，SC20/SC22/SC23 作为 Phase 7 回归场景运行（缓存与意图行为不得回退）。
