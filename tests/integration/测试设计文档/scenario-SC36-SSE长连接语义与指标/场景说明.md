# SC36 SSE 长连接语义与指标

## 1. 场景背景与目的

BFE 在 2026-04-08 增强了 SSE 支持（`936e0be2`）：按请求 `Accept` 与响应 `Content-Type` 识别 SSE，命中后清除客户端读写超时、开启 `cancelOnClientClose`，并在 `proxy_state` 中新增 `SSE_REQ_SERVED` / `SSE_REQ_ACTIVE` 指标。已有场景只把 SSE 当作协议/计费的响应形态，未验证长连接超时、取消与指标本身。

本场景验证：

- 声明 `Accept: text/event-stream` 的请求不被集群写超时切断，超时窗口之后的尾帧仍可送达；
- 非 SSE 响应在同等等待时序下会被写超时切断（对照臂）；
- 响应侧 SSE 识别：`application/sse`、`application/x-sse`、`text/event-stream; charset=utf-8` 同样豁免超时；
- 客户端断开后上游被取消：`SSE_REQ_ACTIVE` 在 backend 仍持有流期间回到 0；
- `proxy_state` 对请求侧/响应侧 SSE 各计数一次，结束后 `SSE_REQ_ACTIVE=0`；
- `Accept` 解析边界：混合大小写与其他 media type 可识别；带 `; q=0.9` 参数后缀的当前不识别。

> 实施发现（现状记录）：请求侧 `Accept` 判定只在普通转发路径生效（`bfe_server/reverseproxy.go:803`）；AI 转发路径（`ServeHTTPForAI`）只在响应侧按 `Content-Type` 判定（`:1404`）。因此 TC-06 以 `EnableAiGateway=false` 运行，用于固定请求侧解析行为；AI 路径的豁免由 TC-01/TC-03 的响应侧 SSE 覆盖。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程；
- AI 后端为进程内 `httptest` mock（SSE 分帧、`SSEHold` 阻塞、可配置 `Content-Type`）；
- Redis 为进程内 miniredis（仅用于 token 规则加载）；
- 不涉及 `ai-gateway-api` 与 `conf-agent`。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | `EnableAiGateway=true`（TC-06 改为 false），加载 `mod_ai_route`、`mod_ai_token_auth` |
| `mod_ai_route/ai_route.data` | `ak_auth` 命中 `cluster_sse` |
| `mod_ai_token_auth/token_rule.data` | 运行时生成：不限量 Key `ak_auth` |
| `server_data_conf/host_rule.data` | `ai_product` 对应 `sse.example.org` |
| `cluster_conf/gslb.data` | `cluster_sse` 单子集群 |
| `cluster_conf/cluster_table.data` / `cluster.conf.data` | 运行时生成；`ClusterBasic.TimeoutWriteClient=300` |

## 4. 测试 Cluster 与配置

- `cluster_sse`：单 mock 后端，`TimeoutWriteClient=300ms`，其余超时使用 harness 默认值；
- mock 后端可配置：`SSEEvents` / `SSETrailing`（首帧与尾帧）、`SSEHold`（首帧后阻塞）、`SSEContentType`、`HoldAfterHeader`（非 SSE 响应先发头再阻塞正文）。
