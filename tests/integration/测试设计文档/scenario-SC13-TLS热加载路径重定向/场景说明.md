# SC13 TLS 热加载路径重定向（conf-agent#19）

## 1. 场景背景与目的

本场景验证 [rainway-ai-gateway/conf-agent#19](https://github.com/rainway-ai-gateway/conf-agent/issues/19) 的 BFE 侧修复在真实 BFE 进程中的行为：conf-agent 触发热加载时通过 `GET /reload/tls_conf?path=tls_conf_<version>` 指定版本化配置目录，BFE 必须把 **client CA / CRL 基目录** 与 `server_cert_conf.data`、`tls_rule_conf.data` 一样重定位到该版本目录，而不是继续读启动时解析的激活目录。

修复前 `ClientCABaseDir`/`ClientCRLBaseDir` 不受 `path` 参数影响：新版本目录中存在、激活目录中不存在的 client CA 会让 `ClientCALoad` 报错，导致 conf-agent 永不切换符号链接，形成"一次失败、永久卡死"（线上 `tls_conf` 因此停留在 7月16日的普通目录，TLS 配置变更全部未生效）。

对应设计文档：`bfe/docs/zh_cn/modifications/2026-09-05-tls-conf-reload-path-fix/design-changes.md`。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程，不涉及 `ai-gateway-api` 与 `conf-agent`；版本化目录由测试代码模拟 conf-agent 的行为生成（完整复制 `tls_conf` 树并按新版本改写 `tls_rule_conf.data`）。
- 通过 BFE https 监听端口的真实 TLS 握手验证 reload 前后行为变化（客户端证书从"不请求"变为"要求并校验"）。
- 客户端证书由测试代码用模板中的 `example_ca` 私钥现场签发。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 https 与 monitor 监听（由 harness 改写为 127.0.0.1 随机端口） |
| `tls_conf/server_cert_conf.data` | 服务器证书配置（`tls_conf/certs/example.crt`） |
| `tls_conf/tls_rule_conf.data` | 基线规则：`ClientAuth=false` |
| `tls_conf/client_ca/example_ca.crt` | 客户端 CA（TC01/TC03 中从激活目录删除以模拟存量死锁现场） |
| `tls_conf/session_ticket_key.data` | 会话票据密钥 |
| `cluster_conf/*`、`server_data_conf/*`、`mod_ai_route/*` | 与 SC01 模板一致，仅保证 BFE 可启动，本场景不代理流量 |

## 4. 测试例清单

| 编号 | 名称 | 一句话描述 |
|------|------|------------|
| TC-01 | 带 path 热加载使用版本目录 client CA | 激活目录缺少 client CA、版本目录存在时，`/reload/tls_conf?path=...` 成功且握手行为随新规则变化（核心回归） |
| TC-02 | 版本目录缺少 client CA 时 reload 报错 | 校验逻辑不变：版本目录缺文件时 reload 返回 `ClientCALoad` 错误 |
| TC-03 | 不带 path 的 reload 保持读激活目录 | 无 `path` 参数时行为与修复前完全一致 |

## 5. 公共断言方式

- reload 结果：解析 monitor 端口返回的 JSON `{"error": ...}`，`error` 为空表示成功。
- 握手行为：`tls.Dial` 到 BFE https 端口，SNI 固定 `example.org`（匹配模板规则的 `SniConf`）。
  - `ClientAuth=false`：无客户端证书握手成功。
  - `ClientAuth=true`（CA 为 `example_ca`）：无客户端证书握手失败；持 `example_ca` 签发的客户端证书握手成功。
