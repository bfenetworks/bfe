# SC27 上游错误体归一

## 1. 场景背景与目的

BFE 协议适配层一期预埋了 `ErrorNormalizer` seam（只服务内部容错决策），上游厂商
错误体一直原样透传：`AIConf.NormalizeUpstreamError`（修改说明见
`docs/zh_cn/modifications/2026-10-06-upstream-error-normalization/design-changes.md`）
补齐了面向客户端的归一：上游错误归一为网关统一错误目录与 OpenAI 兼容响应体，
状态码按统一映射表重映射（上游 401/402/403 → 502 `UPSTREAM_AUTH_ERROR`，与客户端
自身凭证错误的 401 区分），归一链路内嵌 cluster key 脱敏，SSE 流内错误事件
载荷归一、流截断检测入访问日志。

本场景验证：

- 非流式归一：OpenAI/Anthropic envelope 识别与映射、状态码重映射、
  `details.upstream_status`/`upstream_code`、上游消息凭证脱敏（TC-01、TC-02）；
- 未识别错误体：`passthrough`（默认，保状态码、仍脱敏）与 `rewrite_generic`
  （`UPSTREAM_UNKNOWN`）两分支（TC-03、TC-04）；
- 默认关闭基线：不配置时逐字节透传，与历史版本行为一致（TC-05）；
- 归一不影响容错：fallback 重试中不归一，最终结果归一（TC-06）；
- 流式归一：SSE 错误事件载荷改写（OpenAI `data:{"error":...}` 与 Anthropic
  `event: error` 双形态）、SSE 结构保形（TC-07）；
- 流截断检测：无终止事件断流标记 `ai_stream_truncated`，正常 `[DONE]` 与
  Gemini 流（EOF 即正常结束）不标记（TC-08）；
- 网关自生成错误（`X-Bfe-Gw-Error` 标记）不被二次归一（TC-09）；
- 访问日志 810-815 新字段完整性与取值（TC-10）。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程 + **脚本化错误 mock 后端**（测试进程内
  `httptest.Server`，按用例配置返回指定的状态码/响应体/响应头，支持 SSE 流脚本
  与按请求序号切换脚本），不涉及 `ai-gateway-api` 与 `conf-agent`，
  无需 Redis（ak 绑定无限额配额计划）。
- mock 上游两个：`cluster_err`（按 TC 脚本返回错误）、`cluster_fb`（TC-06
  fallback 目标，返回 429）。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 `EnableAiGateway`，加载 `mod_ai_token_auth`、`mod_ai_route`、`mod_access_pb3` |
| `mod_ai_route/mod_ai_route.conf` | 指定 `ai_route.data` 路径 |
| `mod_ai_route/ai_route.data` | apikey 级路由规则（TC-06 含 fallback） |
| `mod_ai_token_auth/mod_ai_token_auth.conf` | 指定 token 规则路径 |
| `mod_access_pb3/mod_access_pb3.conf` | 访问日志（b2log）输出目录，日志断言用 |
| `server_data_conf/host_rule.data` | 声明 `ai_product` 产品线对应的 Host `front.example.org` |
| `server_data_conf/route_rule.data` | 默认路由到 `cluster_err` |
| `cluster_conf/gslb.data` | GSLB 权重配置 |
| `cluster_conf/cluster_table.data` / `cluster_conf/cluster_conf.data` | 运行时根据 mock 后端地址动态生成；`AIConf.Keys` 含 `sk-upstream-secret`，`NormalizeUpstreamError` 按 TC 生成不同变体 |

> 说明：`ai_route.data` 与 `cluster_conf.data` 由测试代码在运行时生成，便于按
> TC 覆盖 `NormalizeUpstreamError` 各字段组合；每个 TC 独立 BFE 实例，配置静态
> 生成一次即可。

## 4. 测试 Cluster 与关键配置

### 4.1 cluster_err / cluster_fb（脚本化错误 mock 后端）

本场景新增公共 helper（`common` 包或 scenario 内 helper）：支持按用例设定

- 非流式脚本：`(status, header, body)` 三元组，可按请求序号切换（TC-06 需要
  同后端先 500 后 429 时不必——TC-06 用两个后端即可，序号切换保留给后续场景）；
- SSE 流脚本：固定字节流（`Content-Type: text/event-stream`），用于错误事件
  改写（TC-07）与截断（TC-08，内容为无终止事件的不完整流）；
- `Hits()` 命中计数——"请求落到哪个 cluster"由哪个后端的 `Hits()` 断言。

### 4.2 AIConf.NormalizeUpstreamError 配置变体

按 TC 生成（字段缺省行为同时被覆盖：缺省 `UnrecognizedAction` → passthrough、
缺省 `MaxBodyBytes` → 65536、缺省 `RedactSecrets` → true）：

| TC | Enabled | StreamEnabled | UnrecognizedAction | RedactSecrets |
|----|---------|---------------|--------------------|---------------|
| TC-01/02/03/06/09 | true | 缺省(false) | 缺省 | 缺省(true) |
| TC-04 | true | 缺省 | rewrite_generic | 缺省 |
| TC-05 | 缺省（整个字段不配置） | — | — | — |
| TC-07/08/10(流式部分) | 缺省 | true | 缺省 | 缺省 |

`AIConf.Keys` 固定（`NormalizeUpstreamError` 测试无关项）：

```json
"Keys": [
    {"Name": "key-primary", "Key": "sk-upstream-secret", "Weight": 100}
]
```

### 4.3 路由表设计

#### apikey_ak_front（TC-01~TC-05、TC-07~TC-10）

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| default | `default_t()` | `cluster_err` | 无 |

#### apikey_ak_fb（TC-06）

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| fb | `default_t()` | `cluster_err` | `cluster_fb` |

#### ApikeyRouteTableBindings

```json
{
    "ak_front": ["apikey_ak_front"],
    "ak_fb": ["apikey_ak_fb"]
}
```

### 4.4 token 规则

- `ak_front` / `ak_fb`：启用、无子网限制、**无限额配额计划**（`unlimited`），
  避免 Redis 依赖；
- TC-09 使用独立 ak（`ak_deny`）：`allow_models=["gpt-4"]`，请求 `deepseek-chat`
  触发本地 `MODEL_NOT_ALLOWED` 拒绝（验证网关自生成错误跳过归一）。

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | OpenAI错误体重写与脱敏 | 上游 401（body 回显 cluster key）→ 502 `UPSTREAM_AUTH_ERROR`、`details.upstream_status=401`/`upstream_code=invalid_api_key`、message 中 key 掩码、响应头 `X-Bfe-Gw-Error: 1`、b2log `ai_err_normalized=true`/`ai_upstream_status=401` |
| TC-02 | 上游429归一与Retry-After | 上游 429 + `Retry-After: 30` + `rate_limit_exceeded` → 429 `UPSTREAM_RATE_LIMITED`、`details.retry_after_seconds=30`；`insufficient_quota` 变体 → `UPSTREAM_QUOTA_EXHAUSTED` |
| TC-03 | 未识别错误体透传与脱敏 | 上游 502 text/html（含 key）→ 状态码 502 与 body 原样透传但 key 被掩码、`ai_err_normalize_miss=true`/`ai_err_normalized=false` |
| TC-04 | 未识别泛化改写 | `rewrite_generic`：502 → 统一 `UPSTREAM_UNKNOWN` 错误体（状态归一为 502、type=internal_error） |
| TC-05 | 开关关闭基线 | 不配置 `NormalizeUpstreamError`：上游 401 原样透传（状态码/逐字节 body）、无 `X-Bfe-Gw-Error` 头、日志 810-815 字段全空 |
| TC-06 | fallback后归一 | 主 cluster 500（`MODEL_INTERNAL_ERROR`）→ fallback cluster 429 → 最终 429 `UPSTREAM_RATE_LIMITED`；两后端 `Hits()` 各 1（fallback 行为不受归一影响） |
| TC-07 | SSE错误事件改写 | 200 SSE 流中 OpenAI 形态错误事件（`data:{"error":...}`）→ data 载荷改写为统一错误 JSON、SSE 结构与状态 200 不变；Anthropic `event: error` 变体同理；`ai_stream_error_rewritten=true` |
| TC-08 | 流截断标记 | 无 `[DONE]` 的不完整流 → 内容透传 + `ai_stream_truncated=true`；正常 `[DONE]` 流与 Gemini 流（EOF 正常结束）不标记 |
| TC-09 | 网关自生成错误跳过 | `MODEL_NOT_ALLOWED` 本地 400 → 响应原样（code 非 `UPSTREAM_*`）、`X-Bfe-Gw-Error` 头存在、归一未介入（日志字段空） |
| TC-10 | 访问日志字段校验 | b2log 解析 810-815 六字段：非流式归一/透传/流式改写/截断/开关关闭各请求的取值矩阵 |

## 6. 公共基础设施

本场景复用既有框架能力：

1. **`common/bfe_config_builder.go`**：运行时生成 `ai_route.data` /
  `cluster_conf.data`（含 `NormalizeUpstreamError` 变体）。
2. **`common/mock_backend.go` 模式**：本场景新增**脚本化错误后端 helper**——
   静态脚本 `(status, header, body)` 或 SSE 字节流，`Hits()` 计数；
   参考 `common/mock_backend.go` 实现， scenario 目录内自带。
3. **b2log 访问日志解析**：复用 SC22 TC-13 的 `accessLogs()` helper 模式，
   断言 810-815 字段（`ai_upstream_status` / `ai_upstream_err_code` /
   `ai_err_normalized` / `ai_err_normalize_miss` / `ai_stream_error_rewritten` /
   `ai_stream_truncated`）。

> 说明：每个测试例拥有独立临时工作目录、独立 BFE 实例、独立 mock 脚本与
> 计数，用例间无状态泄漏；本场景无 Redis/决策服务依赖。

## 7. 与其他场景的依赖关系

- 依赖 SC01（路由表查找与绑定）、SC02（多 API-Key 基础能力与 fallback）；
- 日志断言模式复用 SC05（AI 访问日志字段校验）与 SC22（`accessLogs()` helper）；
- 本场景上线后，SC02/SC05/SC08 作为 Phase 7 回归场景运行（多 Key 轮换、
  日志字段、fallback 行为不得回退）。
