# SC45 推理内容归一化

## 1. 场景背景与目的

部分思考模式模型要求 chat 请求中"最后一条 `user` 消息之后"的 assistant 消息必须携带 `reasoning_content`（缺字段或 `null` 即 400），而这些模型自身存在不产出 reasoning 文本的回合；客户端忠实镜像上游响应时，下一轮必然命中该 400。路由从一个 provider 切到另一个 provider 时更直接：当前轮 assistant 由上一个后端生成，根本不含该字段。

`AIConf.EnsureReasoningContent` 让网关在**上游校验窗口内**补齐空串 `""`。本场景在真实 BFE 进程上验证该机制的数据面行为：只在窗口内补、只增不改、按协议分支、门禁全部 fail-open、多 attempt 幂等、指标可观测。

对应设计文档：

- `bfe/docs/zh_cn/modifications/2026-11-03-ai-reasoning-content-normalization/design-changes.md`（实施记录）
- `bfe/docs/zh_cn/sys_design/ai_reasoning_content_normalization.md`（机制说明）
- `bfe/docs/zh_cn/configuration/server_data_conf/cluster_conf.data.md`（字段配置说明，§9.5）

本场景覆盖的判据是"只多一个字段、其余字节不变"，因此所有断言都以**上游收到的原始请求字节**为准，不用结构化解析断言（结构化解析会漏掉改写误伤）。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程 + 进程内 `httptest` mock 上游，不依赖 ai-gateway-api、conf-agent、Redis、决策服务；
- 客户端为测试进程内的 `http.Client`，请求打到 BFE 监听端口；
- mock 上游记录**收到的原始请求体字节**（`io.ReadAll`）与命中次数，供逐字节断言；
- 计费链路走最小配置（`mod_ai_token_auth` 简单 Token + 集群 ModelTable 单模型价），本场景不校验金额，只保证请求能通过鉴权进入转发。

## 4. 测试 Cluster 与关键配置

### 4.1 cluster_ds（主 cluster）

```json
"cluster_ds": {
    "AIConf": {
        "Type": 0,
        "Provider": "mock-deepseek",
        "ModelProtocols": ["openai", "anthropic"],
        "ProtocolPaths": {"openai": "/v1", "anthropic": "/anthropic"},
        "EnsureReasoningContent": ["openai"],
        "Keys": [{"Name": "key-primary", "Key": "sk-upstream-secret", "Weight": 100}],
        "KeyPolicy": {"Strategy": "weighted_random", "MaxRetries": 0},
        "ModelTable": {"Currency": "RMB", "Models": [{"Name": "deepseek-chat", "Mode": "chat", "Prices": {"input_cost_per_token": 0.000001, "output_cost_per_token": 0.000002}}]}
    }
}
```

配置变体（按用例切换）：

| 用例 | `EnsureReasoningContent` | `ModelProtocols` |
|------|--------------------------|------------------|
| TC-01 | 不配置（基线） | `["openai", "anthropic"]` |
| TC-02、TC-03、TC-06、TC-07、TC-08、TC-09、TC-10、TC-13 | `["openai"]` | `["openai", "anthropic"]` |
| TC-04、TC-05 | `["openai"]` / `["openai", "anthropic"]` | `["openai", "anthropic"]` |
| TC-11、TC-12 | `["openai"]` | `["openai", "anthropic"]` |
| TC-14 | 非法组合（见用例） | 见用例 |

### 4.2 cluster_fb（fallback cluster，TC-07/TC-08）

与 `cluster_ds` 相同，但 `EnsureReasoningContent: ["openai"]`、`Keys` 指向第二个 mock 上游，用于观察"补丁后的请求体再次进入另一个集群"的行为。

### 4.3 路由表设计

- `apikey_ak_front`：target `cluster_ds`；TC-07/TC-08 追加 fallback `cluster_fb`；
- `ApikeyRouteTableBindings`：`ak_front` → `apikey_ak_front`。

### 4.4 请求体样张

窗口内缺字段（TC-02 主样张）：

```json
{"model":"deepseek-chat","messages":[
  {"role":"user","content":"q1"},
  {"role":"assistant","content":"a1"},
  {"role":"user","content":"q2"},
  {"role":"assistant","content":"a2"},
  {"role":"tool","content":"result","tool_call_id":"t1"}
]}
```

其中 `messages[1]` 在窗口之外（历史），`messages[3]` 在窗口内（最后一条 `user` 之后）——只有后者应被补。

## 6. 公共基础设施

1. **`common/process_env.go`**：编译/启动/停止真实 `bfe`，端口自动分配；
2. **`common/bfe_config_builder.go`**：运行时生成 `cluster_conf.data`（含 `EnsureReasoningContent` 变体）与路由/鉴权配置；
3. **`common/mock_backend.go`**：本场景需要一个能**记录原始请求字节**的 mock 上游——在既有 helper 基础上记录 `method`、`path`、`body`（`io.ReadAll`）、`hits`，并支持按脚本返回 200 或 400；
4. **`common/monitor.go`** 的 `ModuleMetric` / `WaitForModuleMetricValue`：读 `proxy_state` 的四个指标（口径同 SC36 的 `SseReqServed` 断言）；
5. **字节断言 helper**：`onlyInsertedFields(t, got, want string, injected ...string)`——把注入片段从响应中剔除后必须与原请求体逐字节相等，这是本场景的核心断言方式。

> 每个测试例使用独立临时工作目录、独立 BFE 实例与独立 mock 计数，用例间无状态泄漏。
