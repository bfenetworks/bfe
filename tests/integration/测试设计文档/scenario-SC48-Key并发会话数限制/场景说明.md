# SC48 Key 并发会话数限制

## 1. 场景背景与目的

AI 网关多 API-Key 集群此前对单把上游 Key 没有任何并发维度保护：任意数量会话可同时压在一把 Key 上。部分上游账号按并发会话授权/计费（如并发 1 的测试账号），需要"一把 Key 同时只服务有限个会话"的硬隔离能力。

变更新增 cluster 级配置 `AIConf.MaxConcurrencyPerKey`（对应控制面 OpenAPI `llm_config.max_concurrency_per_key`，默认 `0`=不限）：

- 对集群内每把 Key 统一生效：同一时刻最多 N 个不同会话（`ClientKeyId`）绑定到一把 Key，同一会话多个并发请求只计 1；
- 占用与 Key 会话亲和性绑定同生命周期：绑定即占用、每次请求命中刷新空闲时间、**空闲超时（`SessionAffinityTTL`）或失败解绑时释放**（不按"最后一个在飞请求结束"释放，避免会话在多把 Key 间 ping-pong 降低 prompt cache 命中）；
- Redis 全局计数（ZSet + Lua 原子脚本，复用 `[AIKeyAffinity]` 句柄），第一期即支持多 BFE 实例精确上限；Redis 未配置/故障时 fail-open。

本场景验证：

- 槽满轮换与合成 429：全部 Key 会话槽满时返回 `NO_AVAILABLE_KEY` 429（`Retry-After` = `SessionAffinityTTL`），零上游交互，正常触发 cluster fallback；
- 已绑定会话不被自挤：占用槽的会话后续（含并发）请求永远命中自己绑定的 Key；
- 失败解绑即时让槽：429/401 轮换路径 ZREM 会话槽，不等 TTL；
- 占用随空闲超时释放（score 过期回收）；
- 默认 0 零开销、Redis 未配置 fail-open、热加载变更 limit 即时生效。

对应变更记录：`bfe/docs/zh_cn/modifications/2026-11-15-ai-key-max-concurrency-per-key/design-changes.md`，设计见 `bfe/docs/zh_cn/sys_design/multi_api_key.md` §3.6。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程 + 进程内 miniredis（`common.RedisServer`）。
- 不涉及 `ai-gateway-api` 与 `conf-agent`。
- 通过 miniredis 直接读取 ZSet 成员（`ZRANGE`/`ZCARD`）断言占用状态。

**可行性已验证**（2026-11-15 预实验）：Lua 脚本（`TIME` + `ZREMRANGEBYSCORE`/`ZSCORE`/`ZCARD`/`ZADD`/`PEXPIRE`）在 miniredis v2.34.0 + redigo 下三分支（新入/判满/刷新）语义全部正确；**注意**：miniredis 脚本内 `redis.call('TIME')` 不随 `FastForward` 走（返回真实时钟），因此"空闲超时释放"用例（TC-05）改用测试侧 `ZADD key <过去时间戳> member` 直接植入"已过期成员"来模拟（效果等价于 `ZREMRANGEBYSCORE` 回收），不依赖 `FastForward`。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 `EnableAiGateway`，加载 `mod_ai_route`、`mod_ai_token_auth`、`mod_ai_rate_limit`，`[AIKeyAffinity]` 指向 miniredis（TC-06 除外：不启用该段验证 fail-open） |
| `mod_ai_route/mod_ai_route.conf` + `ai_route.data` | 定义 apikey 级路由；默认规则命中 `cluster_key_conc`（无 fallbacks），TC-04 使用带 `fallbacks` 的路由表 |
| `mod_ai_token_auth/mod_ai_token_auth.conf` + `token_rule.data` | 定义多个客户端 token（每会话一个，稳定 `key_id` 作 `ClientKeyId`） |
| `mod_ai_rate_limit/mod_ai_rate_limit.conf` + `ai_rate_limit.data` | 放行策略（`rpm` 上限极大），避免限流干扰 |
| `server_data_conf/host_rule.data` | `ai_product` 的 Host 绑定 |
| `server_data_conf/route_rule.data` | 默认路由到 `cluster_key_conc` |
| `cluster_conf/gslb.data` | gslb 权重 |
| `cluster_conf/cluster_table.data` | 运行时按 mock 后端地址生成 |
| `cluster_conf/cluster_conf.data` | 运行时生成，含 `AIConf`（`Keys`/`KeyPolicy`/`MaxConcurrencyPerKey`） |

## 4. 测试 Cluster 与 Key 配置

### 4.1 cluster_key_conc（默认 2 把 Key，max=1）

```json
{
    "AIConf": {
        "Type": 0,
        "Keys": [
            {"Name": "key-a", "Key": "sk-key-a", "Weight": 50},
            {"Name": "key-b", "Key": "sk-key-b", "Weight": 50}
        ],
        "KeyPolicy": {
            "Strategy": "weighted_random",
            "MaxRetries": 3,
            "RetryBackoffInitial": 50,
            "RetryBackoffMax": 200,
            "SessionAffinity": true,
            "SessionAffinityTTL": 300,
            "SessionAffinityRedisPrefix": "bfe:ai:key_affinity",
            "SessionAffinityPenaltyEnable": true
        },
        "MaxConcurrencyPerKey": 1
    }
}
```

> 用例差异：TC-04 的 primary 集群为单 Key（`key-a` Weight 100）且路由带 `fallbacks`；TC-06 不配 `[AIKeyAffinity]` Redis 段；TC-07 热加载把 `MaxConcurrencyPerKey` 由 1 改 2；TC-08 缺省该字段（等价 0）。

### 4.2 Redis 键

```
占用键（ZSet）: bfe:ai:key_affinity:conc:cluster_key_conc:<key_name>
              member = <key_id>（ClientKeyId），score = 过期毫秒时间戳
绑定键:        bfe:ai:key_affinity:cluster_key_conc:<key_id>
惩罚键:        bfe:ai:key_affinity:penalty:cluster_key_conc:<key_name>
```

### 4.3 路由表设计

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| key-conc-default | `default_t()` | `cluster_key_conc` | 无 |
| key-conc-fallback（仅 TC-04） | `default_t()` | `cluster_key_conc_primary` | `cluster_key_conc_fb` |

`ApikeyRouteTableBindings`：默认路由表绑 `ak_conc_a`/`ak_conc_b`/`ak_conc_c`；TC-04 路由表绑 `ak_conc_fb`。

> 默认规则不配 fallback：槽满合成 429 直接返回客户端，便于断言状态码与 `Retry-After`；fallback 行为由 TC-04 专项覆盖。

### 4.4 会话设计

| 客户端 token | key_id（ClientKeyId） | 用途 |
|--------------|----------------------|------|
| `ak_conc_a` | `kid-a` | 会话 A |
| `ak_conc_b` | `kid-b` | 会话 B |
| `ak_conc_c` | `kid-c` | 会话 C（槽满触发者） |

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 槽满轮换与合成 429 | 两会话各占一把 Key 后，第三会话拿到合成 429（`NO_AVAILABLE_KEY`、`Retry-After: 300`），零上游新增交互 |
| TC-02 | 已绑定会话不被自挤与同会话并发 | 占用槽的会话并发 3 请求全成功且命中同一 Key；占用 Key 的 ZSet 成员始终只有 1 个 |
| TC-03 | 失败解绑即时让槽 | 绑定 Key 401 → 同请求轮换成功，原 Key 的 ZSet 成员即时移除，新会话可立即占用 |
| TC-04 | 槽满触发 cluster fallback | primary（单 Key，max=1）槽满 → 合成 429 → fallback 集群 200 |
| TC-05 | 占用随空闲超时释放 | 植入过期成员（score < now）后，新会话可占用该 Key（`ZREMRANGEBYSCORE` 回收路径） |
| TC-06 | Redis 未配置 fail-open | 不配 `[AIKeyAffinity]`，limit=1 不生效：多会话并发全成功、无 conc 键 |
| TC-07 | 热加载变更 limit | 1 → 2 热加载后新会话可入槽，无需重启 |
| TC-08 | 缺省 0 零开销回归 | 不配字段：无 conc 键读写、多会话并发行为同旧 |

## 6. 公共基础设施

1. `common/RedisServer`：本场景新增 `ZMembers(key) []string`（ZRANGE 0 -1）与 `ZCard(key) int64` 读取占用集合；沿用 `TTL`/`FastForward`。
2. `common/BFEConfigBuilder`：按 `AIConfs` 生成 `cluster_conf.data`（`AIConf` 需支持 `MaxConcurrencyPerKey` 字段透传）。
3. `common/MockBackend`：`ResponseFunc` 按请求返回 200/401；`Hits()` 统计上游交互；`AuthHeaders()` 记录注入的 Provider Key（验证会话始终命中自己绑定的 Key）。
4. `common/ProcessEnv`：编译并启动真实 BFE 进程，分配端口；支持热加载（更新 `cluster_conf.data` 后触发 reload，参考 SC46 TC-04）。

## 7. 与其他场景的依赖关系

- 依赖 SC10 已验证的 `ClientKeyId` 绑定与 `[AIKeyAffinity]` Redis 接入；
- 依赖 SC02 已验证的 Key 级失败分类（401 死亡轮换）；
- 依赖 SC46 的 miniredis TTL/热加载设施；
- 合成 429 与 fallback 链路契约来自 #1440/#1441 与 SC47（未选中 targets 并入降级链）。
