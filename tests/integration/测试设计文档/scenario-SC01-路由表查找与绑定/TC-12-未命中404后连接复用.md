# TC-12 未命中 404 后连接复用

## 用例编号与名称

TC-12 未命中 404 后连接复用

## 所属场景

SC01 路由表查找与绑定

## 版本声明

- `bfe`：当前源码版本（含 bfenetworks/bfe#1416 修复：`ServeHTTPForAI` 的 no-route 404 等 AI 路径内部构造响应分支不再设置服务端级 `closeAfterReply`，连接保持 keep-alive 可复用；连接是否关闭交由 HTTP 层按 RFC 2616 语义裁决并带 `Connection: close` 宣告）

## 测试目的

回归验证 bfenetworks/bfe#1416：未命中 AI 路由的内部构造 404 响应发出后，客户端连接必须保持 keep-alive 可复用——同一 client 的第二笔（乃至第 N 笔）no-route 请求在**原连接**上读到完整可读 404，而非 `EOF`/`connection reset`。修复前，no-route 分支在响应后未宣告 `Connection: close` 即关闭连接（服务端级 `action = closeAfterReply`），客户端将死连接投入复用池，第二笔请求失败（issue 对照实验确定性复现 13/13）。

本用例同时锁定边界行为：协议层必须关闭连接的形态（HTTP/1.0、请求头 `Connection: close`、no-route 且 body 排不空）仍**带 `Connection: close` 宣告**关闭，客户端不会误复用——「该留的留、该关的关且必宣告」。

## 运行模式

单组件模式：仅启动真实 `bfe` 进程。

## 前置条件

1. 已编译 `bfe` 可执行文件。
2. mock 后端已启动，所有 cluster 默认返回 200。
3. 临时 BFE 配置已生成并加载，`bfe.conf` 加载 `mod_ai_route` 与 `mod_header` 且 `KeepAliveEnabled = true`。

## 配置构造

- 沿用 TC-03/TC-11 的 no-route 构造：`ApikeyRouteTableBindings` 中不包含 `ak_no_binding`（确保 `mod_ai_route` 未命中、走内部构造 404 路径）。
- `mod_header/header_rule.data`：global 规则 `RSP_HEADER_SET X-Proxied-By: bfe`（本用例在 mod_header 响应回调启用下验证连接复用，即 issue 受治理 fixture 的等价形态）。
- `bfe.conf`：`accessibleBodySize = 4194304`（步骤 4 依赖：4MB 急切缓冲 + `chunk_writer` 256KB 排空间）。
- 测试 client：单个 `http.Client`（`httptrace` 记录每次 `GotConn` 的连接身份与 `Reused` 标志）。注意 Go `http.Transport` 在写请求前探测到死连接时会自动换新连接重试（issue 中 13:10 间歇 PASS 的掩盖来源），因此断言**连接身份相同**而非仅请求成功——换连重试必然改变 Conn 对象，断言失败即暴露掩盖。

## BFE 请求

同一 `http.Client` 顺序执行（Host 均为 `api.example.org`，Path 均为 `/v1/chat/completions`）：

| 步骤 | 请求 | 预期 |
|------|------|------|
| 1 | POST `Authorization: Bearer ak_no_binding`，body `{}` | 404；body 含 `AI route not found`；不宣告关闭（client 侧 `resp.Close=false`）；`httptrace` 记录新连接 C1（`Reused=false`） |
| 2 | 同步骤 1 | 404；body 含 `AI route not found`；**复用 C1**（`Reused=true` 且 `GotConnInfo.Conn` 与 C1 为同一对象） |
| 3 | 3 连发 POST `Authorization: Bearer ak_user_a`（命中路由） | 3×200；3 笔复用同一连接（对照臂：200 路径连接存活，与 issue 人工对照 3/3 一致） |
| 4 | POST `ak_no_binding`，body 5MB（> 4MB 急切缓冲 + 256KB 排空间） | 404；连接**带宣告关闭**：client 侧 `resp.Close=true`（body 排不空，HTTP 层按 RFC 放弃复用） |
| 5 | POST `ak_no_binding`，**HTTP/1.0**（裸 TCP 直连），body `{}` | 404；server 在响应后关闭连接（裸连下一读即 EOF，HTTP/1.0 不复用） |
| 6 | POST `ak_no_binding`，HTTP/1.1 + 请求头 `Connection: close`，body `{}` | 404；`resp.Close=true`（请求头被遵守，带宣告关闭） |

> 断言口径说明：Go `http.Client` 会把响应的 `Connection` hop-by-hop 头从 `resp.Header` 中剥离、其语义反映为 `resp.Close`（已用 httptest 实证：服务端显式回 `Connection: close` 时 client 侧 `resp.Close=true`、`Header.Get("Connection")==""`）。因此测试断言 `resp.Close` 作为「线上是否带 `Connection: close` 宣告」的客户端可见等价信号。另外 Go `http.Transport` 在线上恒发送 HTTP/1.1（设置 `req.Proto="HTTP/1.0"` 无效，已实证），故步骤 5 的 HTTP/1.0 请求改用裸 TCP 直连构造。

## 预期结果

- 步骤 1–3：连接复用断言全部成立；响应头 `X-Proxied-By: bfe` 存在（mod_header 全局规则作用于内部 404，与连接复用兼容，即 #1359 与 #1416 两个修复的组合形态）。
- 步骤 4–6：三种协议层关闭形态均**带宣告**关闭（client 侧 `resp.Close=true`），客户端不会把死连接投入复用池。
- mock 后端命中：步骤 1/2/4/5/6 全部 cluster 为 0；步骤 3 命中 apikey 路由表绑定的 cluster（a/b/c 之一）。

## 清理

停止 `bfe` 进程与所有 mock 后端，删除临时目录。
