# TC-14-终态字段与文件内容统计落库

## 目的

验证 issue #254 的数据面修复：批量任务在 `completed` 终态后，`BATCH_TASK` / `BATCH_FILE` 两个哈希携带**控制面契约所需的全字段**，且行数/字节描述**文件内容**而非 multipart 信封。

覆盖的缺陷（修复前实测）：`BATCH_TASK` 只有 `api_key_id/cluster/key_name/input_file_id/est_lines/status/reserved` 七个字段，`output_file_id`/`request_counts`/`endpoint`/`created_at`/`reserved_units` 缺失，`settle_status` 永驻 `reserved`（`usage_in`/`usage_out`/`settle_units`/`usage_source` 永不写入）；`BATCH_FILE.lines/bytes` 统计的是出站 multipart 整体（1 行 / 206 字节被记为 11 行 / 509 字节）。

## 前置条件

见 `../场景说明.md` §2/§3（真实 bfe + miniredis + mock provider，tc 级 rule data 由测试代码生成）。本用例特有：

- 结果文件使用 OpenAI Batch 真实契约形态——usage 位于 `response.body.usage`（`resultJSONLBody`，两行 `gpt-4o`，`prompt/completion = 10/5` 与 `3/2`）。
- mock provider：`POST /v1/files` 返回 File 对象 `{"id","purpose":"batch","bytes":<content>,"filename":"batch-input.jsonl"}`；`POST /v1/batches` 与 `GET /v1/batches/{id}` 返回 `endpoint`、`created_at`、`request_counts`。
- 上传内容 `inputJSONL`（2 行，216 字节级），multipart 信封明显大于内容。

## 请求构造

| 步骤 | 请求 |
|------|------|
| 上传 | `POST /v1/files`，`multipart/form-data`：`file` part（文件名 `batch-input.jsonl`，内容 `inputJSONL`）+ 字段 `purpose=batch` |
| 创建 | `POST /v1/batches`，body `{"input_file_id":"file-in-1","endpoint":"/v1/chat/completions","completion_window":"24h"}` |
| 查询 | `GET /v1/batches/batch-1` |
| 下载 | `GET /v1/files/file-out-1/content`（触发下载拦截结算） |

## 后端响应

- 上传：`200 {"id":"file-in-1","object":"file","purpose":"batch","bytes":<len(content)>,"filename":"batch-input.jsonl"}`
- 创建：`200 {"id":"batch-1","object":"batch","status":"in_progress","input_file_id":"file-in-1","output_file_id":"file-out-1","endpoint":"/v1/chat/completions","created_at":1760000000,"request_counts":{"completed":0,"failed":0,"total":2}}`
- 查询：`200 {"id":"batch-1","status":"completed","input_file_id":"file-in-1","output_file_id":"file-out-1","endpoint":"/v1/chat/completions","request_counts":{"completed":2,"failed":0,"total":2}}`
- 下载：`200` + `resultJSONLBody`（`response.body.usage` 形态）

## 执行步骤

1. 启动 BFE（RMB 计划余额充足，ModelTable 含 `gpt-4o` 的 chat/batch 双价）。
2. 依次执行上传 → 创建 → 查询。
3. 读 `BATCH_FILE:cluster_batch:file-in-1`、`BATCH_TASK:batch-1`（miniredis `HGetAll`），断言 §预期结果 A/B。
4. 读 `mod_ai_batch` 计数器基线：`SETTLE_USAGE_PARSE=0`、`TASK_SETTLE_WRITE=0`。
5. 下载输出文件，`waitForRedis` 等到结算落库。
6. 再次读 `BATCH_TASK:batch-1` 与计数器，断言 §预期结果 C/D。
7. 读 `BATCH_FILE:cluster_batch:file-out-1`，断言输出绑定（`dir=output`、`batch_id`）。

## 预期结果

**A. 输入文件绑定（`BATCH_FILE:<cluster>:file-in-1`）**

| 字段 | 期望 |
|------|------|
| `lines` | `2`（文件内容行数，等于 `wc -l inputJSONL`） |
| `bytes` | `len(inputJSONL)`（等于 `wc -c`，**不是** multipart 信封长度） |
| `filename` | `batch-input.jsonl`（File 对象给出） |
| `lines_src` / `bytes_src` | `exact`（file part 已定位 + File 对象字节数） |
| `purpose` / `dir` | `batch` / `input` |
| `api_key_id` | `ak_batch` |

**B. 创建期任务记录（`BATCH_TASK:batch-1`，查询前）**

| 字段 | 期望 |
|------|------|
| `status` | `in_progress` |
| `input_file_id` | `file-in-1` |
| `output_file_id` | `file-out-1`（创建响应已带） |
| `endpoint` | `/v1/chat/completions`（来自创建请求体） |
| `request_counts` | `{"completed":0,"failed":0,"total":2}` |
| `created_at` | `1760000000`（provider unix 秒） |
| `est_lines` | `2`（取自输入文件绑定的内容行数） |
| `reserved_units` | `>0`，且等于 `est_lines × (ReserveInputTokens+ReserveOutputTokens) × 批量价` 口径下的 RMB 定点值（本用例只断言 `>0` 与 `reserved=1`） |
| `reserved` | `1` |
| `usage_in`/`usage_out`/`settle_units`/`settle_status`/`usage_source` | **均不出现**（尚未结算，`settle_status` 缺省由控制面读作 `reserved`） |

**C. 查询后任务记录（`BATCH_TASK:batch-1`）**

| 字段 | 期望 |
|------|------|
| `status` | `completed` |
| `output_file_id` | `file-out-1` |
| `endpoint` | `/v1/chat/completions` |
| `request_counts` | `{"completed":2,"failed":0,"total":2}`（`get` 覆盖创建期的 0 计数） |

**D. 下载结算后任务记录 + 计数器**

| 字段/计数器 | 期望 |
|------|------|
| `usage_in` / `usage_out` | `13` / `7`（两行 `response.body.usage` 汇总） |
| `settle_units` | `2700`（= (13×1 + 7×2)μ 元 → 2700 个 1e-8 单位，同 TC-02 口径） |
| `settle_status` | `settled` |
| `usage_source` | `download`（下载拦截结算标记，控制面只在兜底结算写 `reconcile`） |
| `mod_ai_batch.SETTLE_USAGE_PARSE` | `1`（下载拦截解析成功） |
| `mod_ai_batch.TASK_SETTLE_WRITE` | `1`（finish 阶段按结算结果回写） |
| `mod_ai_batch.SETTLE_NO_USAGE` / `SETTLE_USAGE_PARSE_ERR` | `0` / `0` |
| `mod_ai_batch.UPLOAD_COUNT_APPROX` | `0`（上传命中 file part，未降级为信封计数） |
| `BATCH_SETTLED:batch-1` | 存在 |

**E. 输出文件绑定（`BATCH_FILE:<cluster>:file-out-1`）**：`dir=output`、`batch_id=batch-1`、`api_key_id=ak_batch`。

## 观测点

miniredis 哈希（`common.RedisServer.HGetAll`，本用例新增）、`mod_ai_batch` 模块计数器（`common.ModuleMetric`：`SETTLE_USAGE_PARSE` / `SETTLE_NO_USAGE` / `SETTLE_USAGE_PARSE_ERR` / `TASK_SETTLE_WRITE` / `UPLOAD_COUNT_APPROX`）、访问日志（`ai_batch_settle=settle`）。

## 清理

`testEnv.Close()`：停 BFE、关 mock provider、关 miniredis（端口由框架分配，无残留）。

## 说明

- `est_lines` / `reserved_units` 只断言"内容行数"与"非零"，不锁死金额公式：预留系数（`ReservePerLineMicros` / `ReserveInputTokens` / `ReserveOutputTokens`）是运营可调配置，锁死会让本用例随配置漂移（金额口径由 TC-02 / TC-12 负责）。
- `settle_units=2700` 与 TC-02 的余额扣减断言同源（同一 fixture、同一批量价），此处只读哈希而不读余额，用于验证"结算金额确实落库"。
