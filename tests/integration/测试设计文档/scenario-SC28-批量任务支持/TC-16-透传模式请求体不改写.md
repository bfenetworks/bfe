# TC-16-透传模式请求体不改写（target model 非空）

## 目的

验证 AI 路由 target model 非空时，provider 原生批量端点的请求体**逐字节透传**、不被网关改写（[bfenetworks/bfe#1426](https://github.com/bfenetworks/bfe/issues/1426)）：

1. `POST /v1/files`（mode=file）的 multipart 原始字节（boundary、part 头、文件内容）与 `Content-Type`/`Content-Length` 原样到达 provider——不得被替换为 `{"model":"<target>"}`；
2. `POST /v1/batches`（mode=batch）的创建 JSON 不得被注入额外的 `model` 字段；
3. 对照：同一路由下 `POST /v1/chat/completions`（mode=chat）的 target model 覆盖**仍然生效**（聊天改写语义不受影响）。

覆盖的缺陷（修复前实测，issue #1426）：`doSingleAIForward` 的 model 改写判定未检查透传模式与 Content-Type，`/v1/files` 的 multipart 体被 `sjson` 整体替换为单行 JSON，provider 返回 `400 multipart: NextPart: EOF`；`/v1/batches` 的 JSON 体被静默注入 `model` 字段。

## 前置条件

见 `../场景说明.md` §2/§3。本用例特有：

- mock provider 增加 `POST /v1/chat/completions` 端点：解析请求体 JSON，原样返回 `{"model":<请求体中的 model>}`，使测试能读回改写后的 model 值；
- mock provider 记录每次请求到达时的 `Content-Type` 与 `Content-Length` 头（用于透传断言）；
- 路由 target model 非空：`ai_route.data` 中 `cluster_batch` 的 target `Model` 设为 `controlled-batch-model`（仅本用例的 conf 生效，不影响其他用例）。

## 请求构造

| 步骤 | Method | Path | Headers | Body |
|------|--------|------|---------|------|
| 1 | POST | `/v1/chat/completions` | `Authorization: Bearer ak_batch`、`Content-Type: application/json` | `{"model":"gpt-4o","messages":[{"role":"user","content":"hi"}]}` |
| 2 | POST | `/v1/files` | 同上（multipart 由 `mime/multipart` 生成） | `purpose=batch` 字段 + `file` 字段（文件名 `batch.jsonl`，内容为一行合法 batch JSONL） |
| 3 | POST | `/v1/batches` | `Content-Type: application/json` | `{"input_file_id":"file-in-1","endpoint":"/v1/chat/completions","completion_window":"24h"}`（**无** `model` 字段） |

## 后端响应

| 端点 | 响应 |
|------|------|
| `POST /v1/chat/completions` | `200` + `{"model":"<请求体回显>"}` |
| `POST /v1/files` | `200` + File 对象（同 TC-01） |
| `POST /v1/batches` | `200` + Batch 对象（同 TC-01） |

## 执行步骤

1. 启动 BFE（余额充足；conf 构建后将 `ai_route.data` 中 target `Model` 由 `""` 改为 `controlled-batch-model` 再启动）。
2. 依次发送上述三个请求。
3. 读 mock provider 记录的三次请求体与头：
   - chat：解析记录体 JSON，取 `model`；
   - files：用 `extractMultipartFile` 按记录的 `Content-Type` 解析记录体，取 `file` part 内容；
   - batches：记录体按 JSON 解析。
4. 访问日志复核 `mode` 与 `ai_target_model` 字段。

## 预期结果

| 断言 | 期望 |
|------|------|
| A. chat 改写仍生效 | provider 收到 chat 请求体的 `model == "controlled-batch-model"`（target model 覆盖未被守卫误伤） |
| B. files 体逐字节透传 | `extractMultipartFile` 解出的文件内容**逐字节等于**客户端发送的 JSONL；记录的 `Content-Type` 以 `multipart/form-data; boundary=` 开头且与客户端一致；`Content-Length` 与客户端原始体长度一致（未被置 `-1`） |
| C. batches 不注入 | provider 收到的 batches 请求体**不含** `model` 字段，其余字段与客户端原样一致 |
| D. 访问日志 | 三行 `ai_target_model` 均为 `controlled-batch-model`；files/batches 行 `ai_requested_model` 为空、`mode` 分别为 `file`/`batch`（旁路记录不受守卫影响） |

## 观测点

mock provider 记录的请求体与头（`RequestBodies()` + handler 内记录）、访问日志 `ai_mode`/`ai_target_model`。

## 清理

同 TC-14（`testEnv.Close()`）。

## 说明

- 修复前本用例的 B/C 断言确定性失败（multipart 被替换为 `{"model":"controlled-batch-model"}`，provider 侧按 multipart 解析拿到 EOF 型错误，File 对象不返回）；修复后全部通过。
- 单元测试 `bfe_server.TestShouldRewriteBodyModel` 直接覆盖 `shouldRewriteBodyModel` 的守卫真值表（含 `+json` 后缀、头缺失/非法不拦截等边界）；本用例在真实转发链路上做端到端印证，两者互补。
