- 计数器读数：`testEnv.monitorPort` 由 `StartBFERaw` 捕获，用例经 `common.ModuleMetric` / `common.WaitForModuleMetric` 读 `mod_ai_token_auth` 计数器（`/monitor/mod_ai_token_auth?format=prometheus`，键为 SNAKE_CASE，如 `mod_ai_token_auth_BILLING_ZERO_COST`）

## 前置条件

见 `../场景说明.md` §2/§3（真实 bfe + miniredis + mock provider，tc 级 rule data 由测试代码生成）。本用例特有：`withNoBatchPrice` 去掉 ModelTable 的 `batch` 行、只保留 `gpt-4o` 的 `chat` 行（`input 2e-6`、`output 4e-6`）；下载结果文件 `resultJSONL` 两行同为 `gpt-4o`。

## 测试步骤与断言

AIConf ModelTable 仅配 chat 价（无 batch 行）。完整生命周期+下载（结果文件含 usage）→ 结算查价 miss 计 0 费：余额不变、日志 ai_batch_settle=settle。

issue #1414 追加断言（原有断言保留）：

- 结算计费为 0 时：`PriceLookupMiss` +1（#1408 既有信号，非本 issue 新增）、`BillingZeroCost` +1、下载行 `ai_zero_cost_reason=price_miss`。
- 计数基线（新语义，2026-10-13 产品调整）：收口点条件为 `costUnits == 0 && hasRMBPlan(...) && ctx.aiBasicInfo.TargetModel != ""`（`bfe_modules/mod_ai_token_auth/mod_ai_token_auth.go:521`）。生命周期的三个控制请求（upload / create / get）虽绑定同一 API Key 与 RMB 计划、计费为 0，但**从未成为模型调用**（无 target model），零成本属设计而非异常，故被排除：**结算前基线 `BillingZeroCost == 0`、`PriceLookupMiss == 0`；下载结算后两者各为 `1`**（AI 缓存命中原有的早退排除不变；批量结算路径自有的收口点见下条，不受该排除影响）。修复前（无 `TargetModel` 条件）这三个控制请求各计 1 次，整条 lifecycle 后为 4，会把每个 batch 生命周期的告警基数抬高 3。
- 排除的反向证明（集成层，本用例实跑）：三个控制请求均已结束（等待 `get` 行的访问日志记录出现，保证其 finish handler 已执行）时基线为 0，且 4 个请求结束后计数器恰为 1——若控制请求被计数，终值必为 4。故 `BillingZeroCost`/`PriceLookupMiss` 的 `0 → 1` 同时证明"控制请求被排除"与"结算被计数"。
- 计数口径：settle 按行内 model 分组遍历（`batch_quota.go:256-271`），fixture 两行同为 `gpt-4o` 即 1 组，故 `PriceLookupMiss == 1`、`BillingZeroCost == 1`（批量结算路径的收口点为 `batch_quota.go:288-297`，独立于标准收口点，不受 `TargetModel` 排除影响）；多 model 的 fixture 需按组数调整期望值。
- 原因码来源：价表 miss 分支显式写入 `ZeroCostReasonPriceMiss`（`bfe_modules/mod_ai_token_auth/batch_quota.go:263-264`），收口点沿用已埋原因码、不再兜底为 `batch_release`。
- 可顺带断言（#1414 同批新增的行级信号，非本用例核心）：下载行 `ai_price_miss=true`（批量 price miss 此前只有计数器 + Warn，行级不可查，`batch_quota.go:263`）与 `ai_cost_value=0`（已观测 2xx 行显式写出 0）。
- **不要断言 `ai_usage_source`**：该字段在下载行缺席——批量结算在 `tokenRequestFinishHandler` 的 usage-source 判定点之前返回（`mod_ai_token_auth.go:384-386`），故其取值不会被设置（断言为 `parsed` 之类会失败）。
- **已知残差（如实登记，本用例不断言）**：控制请求的**行级**原因码未被同一条件收敛——`calcCostUnits` 在 `clusterName == "" || targetModel == ""` 的早退点自行 `SetZeroCostReason(config_missing)`（`mod_ai_token_auth.go:916-918`），而访问日志对任何非空原因码都会写出（`mod_access_pb3/request_log.go:501-507`），因此 upload/create/get 行仍带 `ai_zero_cost_reason=config_missing`（实跑观测：`get` 行 = `config_missing`）。即本次收敛是**计数器/Warn 级**的（收口点 Warn 也已随排除消失），行级标记是否同样收敛待 owner 决定；本用例只以计数器基线为排除证据，不断言该行原因码缺席。

`batch_release` 说明（另一条零计费形态，本场景**无对应 TC、本 issue 不新增**）：`batch_release` 只在**结算路径**的兜底分支产生——settle 算出 `costUnits == 0` 且此前没有更具体的原因码时，`reason` 兜底为 `batch_release` 并计 `BillingZeroCost`（`bfe_modules/mod_ai_token_auth/batch_quota.go:288-297`，语义即"结算未计费、预留随之释放"）。它与本 TC 的 `price_miss` 是两个不同分支（`price_miss` 由价表 miss 分支显式埋码，收口点沿用，不再回落 `batch_release`）。

**不能登记在 TC-05/TC-09**：取消与失败终态释放（TC-05/TC-09 的 `ai_batch_settle=release`）走的是 `BatchRelease`（`batch_quota.go:184-219`）——它只清预留镜像并占位 `BATCH_SETTLED`，**既不进入收口点、也不打原因码、不计 `BillingZeroCost`**。因此该场景现有用例中没有任何一条命中 `batch_release`，`batch_release` 的覆盖需另加"结算 0 费且无更具体原因"的形态（fixture 结果文件行内 usage 全 0、价表齐全），属新增用例，**超出本 issue 范围，未新增**（此为与 issue #1414 方案文档 §五 第 8 条"release 未计费臂"的偏差：落地后该原因码只由结算兜底产生，释放路径不产生信号）。

## 观测点

访问日志（`common.ParseAccessLog`；`batchLogEntry` 已扩展承载 `ai_zero_cost_reason`（含是否写出）/ `ai_price_miss`（含是否写出）/ `ai_cost_value`（含是否写出），下载行与 `get` 行的字段均从该结构读取）、miniredis 键值、mock 后端命中记录、`mod_ai_token_auth` 模块计数器（`common.ModuleMetric` 读 monitor 端口：`BillingZeroCost` / `PriceLookupMiss` / `UsageUnrecognized`）。实现为 `sc28_ai_batch_test.go` 的 `TestTC11_NoBatchPriceBillsZero`；为在结算前取基线，lifecycle 拆为 `runLifecycleToDownload`（upload/create/get）+ `downloadResult`（下载，触发结算），`runLifecycle` 仍按原四步组合、行为与报错文本不变。
