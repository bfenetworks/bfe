# TC-09 首次选 Key 失败返回合成 429 并触发 cluster fallback

## 用例编号与名称

TC-09 首次选 Key 失败返回合成 429 并触发 cluster fallback（issue #1440）

## 所属场景

SC02 多 API-Key 轮换与重试

## 版本声明

- `bfe`：v1.8.9-dev 分支 + issue #1440 修复（`aiClusterInvoke` 返回统一 AiError 形态的合成 429；`shouldTriggerFallback` 对 nil/nil 视为可降级）

## 测试目的

验证当集群**一次选 Key 都未成功**（本用例构造：全部 Key `Weight=0`，`chooseNextAIKey` 首轮即返回 `ok=false`，未发起任何上游请求）时：

- `aiClusterInvoke()` 不再返回 `(res=nil, err=nil)`，而是返回**合成 429 响应**（统一 AiError 目录：`UPSTREAM_RATE_LIMITED` / `rate_limit_error`，body 为 `{"error":{"code":"UPSTREAM_RATE_LIMITED","type":"rate_limit_error",...}}`，带 `X-Bfe-Gw-Error: 1` 网关标记），且**不设置** `basicReq.ErrCode`（尤其不得是 `ErrAiRateLimit`，否则会触发 local-RL 的 fallback 禁止短路）；
- 外层 `ServeHTTPForAI()` 的 `shouldTriggerFallback` 因 429 命中 `aiFallbackStatusCodes` 白名单，**触发 cluster fallback**，命中备用集群并成功；
- 臂 B（无 fallback 路由）：客户端直接收到合成 429（而非网关 500），响应 body 非空且为统一错误 JSON；
- 网关标记保证 `normalizeUpstreamError`（`AIConf.NormalizeUpstreamError`）不会对该响应做二次改写。

与 TC-05/TC-06 的区别：TC-05/06 的耗尽发生在**至少一次上游交互之后**（`res` 为最后一次真实上游响应）；本用例的耗尽发生在**首次选 Key 阶段**，修复前该路径返回 `(nil, nil)`，`shouldTriggerFallback` 得到 `status=0`，fallback 完全不生效，请求落为 500——即 issue #1440 的现场路径。

## 运行模式

单组件模式：仅启动真实 `bfe` 进程。

## 前置条件

1. 已编译含 issue #1440 修复的 `bfe` 可执行文件。
2. mock 后端已启动。
3. 临时 BFE 配置已生成并加载。
4. `common/bfe_config_builder.go` 已支持按 cluster 注入 `AIConf`（SC02 既有能力）。

## 配置构造

- `cluster_multi_key.AIConf`（本用例通过 `newTestEnv(t, aiConf)` 注入，覆盖场景默认值）：
  - `Keys`：`[{Name:"key-a", Key:"sk-key-a", Weight:0}, {Name:"key-b", Key:"sk-key-b", Weight:0}]`（全部 `Weight=0`，任何一轮选择都无候选）；
  - `KeyPolicy.MaxRetries`：1（与现场一致；无论重试几轮，候选恒为空）。
- 臂 A 路由：`user_a-multikey`（`multikey.example.org`），targets=`cluster_multi_key`，fallbacks=`cluster_fallback_ok`（testdata 既有）。
- 臂 B 路由：新增 `user_a-multikey-nofallback`（`multikey-nofallback.example.org`），targets=`cluster_multi_key`，**无 fallbacks**（本 TC 落地时同步加入该场景 testdata）。
- `cluster_fallback_ok` 后端行为：返回 200 `{"ok":true}`。

## BFE 请求

| 字段 | 臂 A | 臂 B |
|------|------|------|
| Host | `multikey.example.org` | `multikey-nofallback.example.org` |
| Path | `/v1/chat/completions` | 同左 |
| Authorization | `Bearer ak_user_a` | 同左 |
| Body | `{"model":"gpt-4"}` | 同左 |

## 执行步骤

1. 以全部 `Weight=0` 的 `AIConf` 启动 BFE（臂 A 用既有路由；臂 B 用无 fallback 路由）。
2. 发送请求。
3. 读取响应状态码与 body。
4. 检查 `cluster_multi_key` mock 后端命中次数与 `cluster_fallback_ok` 命中次数。
5. 检查 BFE 运行日志（`log/bfe.log`）中是否出现：
   - `aiClusterInvoke: all ai keys exhausted for cluster[cluster_multi_key], return synthetic 429`；
   - 臂 A：`ServeHTTPForAI: fallback triggered, cluster[cluster_multi_key] err[<nil>] status[429]`。

## 预期结果

**臂 A（有 fallback）**：

- 响应状态码：200，body 为 `{"ok":true}`（来自 `cluster_fallback_ok`）。
- `cluster_multi_key` 后端命中 **0** 次（选 Key 即失败，未发起上游请求）。
- `cluster_fallback_ok` 后端命中 1 次。
- BFE 日志同时出现上述两条记录。
- 不出现 `res=nil` 形态的 500；exception.log 无新增 panic/异常。

**臂 B（无 fallback）**：

- 响应状态码：**429**（不是 500）。
- 响应 `Content-Type: application/json`，body 解析后 `error.type == "rate_limit_error"`。
- **`error.code == "NO_AVAILABLE_KEY"`**（issue #1441：统一错误体必填字段）。
- **HTTP `Retry-After` 响应头存在**（秒数形式，值 = `error.details.retry_after_seconds` = 429 惩罚 TTL 60s）（issue #1441 退避信号）。
- `cluster_multi_key` 后端命中 0 次。
- 响应头 `Server: bfe`（合成响应由 BFE 生成）。

## 清理

停止 `bfe` 进程与所有 mock 后端，删除临时目录。

## 备注

- 本用例**不依赖 Redis**：`KeyPolicy.SessionAffinity` 使用默认值（false），不进入惩罚过滤路径；它隔离验证 #1440 本身的契约（耗尽 ⇒ 可判定结果），#1439 的惩罚过滤口径由 SC02 既有 TC-02 及后续 #1439 专用 TC 覆盖。
- 全部 Key `Weight=0` 是触发"首次选 Key 即失败"的最简构造；生产现场（#1439 触发后）等价路径是"可用 Key 全部被惩罚，仅剩 `Weight=0` 候选"，两者在 `chooseNextAIKey` 层收敛到同一个 `ok=false` 出口。
- v1.8.9-dev 差异：合成 429 采用统一 AiError 目录形态（`AiError.CreateErrorResponse`），自带 `X-Bfe-Gw-Error: 1`，`normalizeUpstreamError` 对其跳过；v1.8.8 反向移植版使用普通 JSON 响应（该分支无统一错误目录与归一化器）。
