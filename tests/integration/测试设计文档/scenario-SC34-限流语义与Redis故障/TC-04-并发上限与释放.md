# TC-04 并发上限与释放

## 用例编号与名称

TC-04 并发上限与释放

## 所属场景

SC34 `mod_ai_rate_limit` 分布式限流语义

## 版本声明

- `bfe`：当前源码版本

## 测试目的

验证 `max_concurrency` 的准入与请求结束后的槽位释放：并发请求在槽位被占用时被拒绝，占用方结束后恢复。

## 运行模式

单组件模式：仅启动真实 `bfe` 进程；AI 后端为进程内 mock，Redis 为进程内 miniredis。

## 前置条件

1. 已编译 `bfe` 可执行文件。
2. 嵌入式 Redis 已启动；mock 后端 `cluster_rl_main`、`cluster_rl_fallback` 已启动，返回固定 usage（prompt=100, completion=50, total=150）。
3. `bfe.conf` 中 `EnableAiGateway=true`，加载 `mod_ai_token_auth`、`mod_ai_route`、`mod_body_process`、`mod_ai_rate_limit`、`mod_access_pb3`。
4. `ai_route.data` 中 `ak_sc34` 命中 `cluster_rl_main`，fallback 为 `cluster_rl_fallback`。
5. `token_rule.data` 绑定 `ak_sc34` 到不限量配额计划，保证鉴权不干扰限流。

## 配置构造

- 限流策略 `rlp-sc34`：`max_concurrency=1`。
- mock 后端 `ResponseFunc` 在 `release` channel 关闭前阻塞，用于让请求 A 长时间持有槽位。

## BFE 请求

| 步骤 | Host | Path | Authorization | Body | 说明 |
|------|------|------|---------------|------|------|
| 1 | rl.example.org | /v1/chat/completions | Bearer ak_sc34 | {"model":"gpt-4"} | 请求 A，后端阻塞 |
| 2 | rl.example.org | /v1/chat/completions | Bearer ak_sc34 | {"model":"gpt-4"} | 并发请求 B（A 未完成） |
| 3 | rl.example.org | /v1/chat/completions | Bearer ak_sc34 | {"model":"gpt-4"} | 释放 A 后的请求 C |

## 预期结果

- 请求 A 到达后端后（`Hits()==1`），请求 B 返回 429，`error.code=CONCURRENCY_LIMIT_EXCEEDED`。
- 关闭 `release` 后请求 A 返回 200；随后请求 C 轮询至 HTTP 200（槽位已释放）。
