# SC34 `mod_ai_rate_limit` 分布式限流语义

## 1. 场景背景与目的

`mod_ai_rate_limit` 自 2026-07-01 引入，用 Redis 实现 AI 请求的分布式限流；2026-07-17 将 RPM 从 GCRA 改为滑动窗口，2026-07-08 增加 `is_redis_error` 与 `IsRejectOnRedisError` 故障语义。已有场景只覆盖了 `redis_key` 计数器连续性（SC07）与「适用模型」按目标模型匹配（SC19）、RPM 拒绝的错误体（SC05 TC-07），限流器本身的窗口、TPM、并发与 Redis 故障语义没有进程级回归。

本场景验证：

- RPM 滑动窗口的计数边界与窗口滑过后的恢复（含 Redis TIME 语义）；
- TPM 的超限拒绝与按真实 usage 记账；
- `max_concurrency` 的准入与释放；
- Redis 故障时 `IsRejectOnRedisError=true/false` 的 fail-closed / fail-open 行为与访问日志 `redis_error` 命中；
- 多策略绑定、禁用策略、未绑定 Key 的行为；
- 规则热加载；
- 本地限流拒绝不轮换 provider key、不触发集群 fallback。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程；
- AI 后端为进程内 `httptest` mock，Redis 为进程内 miniredis（可注入故障、可推进虚拟时钟）；
- 不涉及 `ai-gateway-api` 与 `conf-agent`。

## 4. 测试 Cluster 与配置

### 4.1 拓扑

- `cluster_rl_main`：主后端，返回固定 usage（prompt=100, completion=50, total=150）；
- `cluster_rl_fallback`：fallback 后端，仅在用例需要时被命中（本场景断言其 0 命中）；
- 两个 cluster 的 `AIConf` 默认 1 个 provider key；TC-09 使用 2 个 key + `MaxRetries=2`。

### 4.2 限流规则矩阵

| 用例 | 策略内容 | 关键参数 |
|------|----------|----------|
| TC-01 | RPM | `max_requests=2`、`window_minutes=1`、`redis_key=default_bfe_sc34_rpm` |
| TC-02/03 | TPM | `max_tokens=100/100000`、`window_minutes=1`、`step_minutes=1`、`redis_key=default_bfe_sc34_tpm` |
| TC-04 | 并发 | `max_concurrency=1` |
| TC-05/06 | RPM（Redis 故障） | `max_requests=100`；`IsRejectOnRedisError=true/false` |
| TC-07 | 多策略 | 策略 0：RPM=1（enabled）；策略 1：RPM=1（disabled）；绑定关系见用例 |
| TC-08 | 热加载 | 初始 RPM=1，reload 前改为 100 |
| TC-09 | RPM + 多 Key + fallback | `max_requests=1` |

## 5. 公共断言口径

- 拒绝响应为 `AiError` 统一错误体：`error.code` ∈ {`RPM_LIMIT_EXCEEDED`, `TPM_LIMIT_EXCEEDED`, `CONCURRENCY_LIMIT_EXCEEDED`, `RATE_LIMIT_REDIS_ERROR`}，HTTP 429（Redis 错误 500），`details.limit_type` 对应 `rpm/tpm/concurrency/redis_access_error`；
- 请求一律使用 `DisableKeepAlives` 的独立客户端：本地拒绝会关闭连接，复用连接会让后续 POST 收到 EOF；
- 时间推进使用 `RedisServer.AdvanceTime`（同时推进 TIME 与 key TTL），RPM 窗口断言使用 90s 余量；
- TPM 记账通过轮询 `default_bfe_sc34_tpm` 哈希累计值确认。
