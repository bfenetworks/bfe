# SC49 访问日志 Header 白名单采集与动态配置热加载

## 1. 场景背景与目的

`bfe-access_pb` 协议的 `RequestLog` 自发布起即预留通用 KV 列表字段 `req_headers`（55）/`res_headers`（158），但 `mod_access_pb3` 从未实现采集逻辑，访问日志经 log-reader → Kafka → Doris 后两列恒空。业务需要按白名单采集请求头/响应头（如 `business_type`、`x-request-id`、`x-trace-id`），用于流量分析、按业务维度聚合与问题排查（需求来源：[bfenetworks/bfe#1506](https://github.com/bfenetworks/bfe/issues/1506)）。

变更（`bfe/docs/zh_cn/modifications/2026-11-15-issue-1506-mod-access-pb3-header-whitelist/design-changes.md`，设计见 `bfe/docs/zh_cn/sys_design/mod_access_pb_data_conf.md`）：

- 白名单等动态配置放独立 JSON 数据文件 `mod_access_pb.data`（多段式通用载体，首段 `access_header`）；静态配置 `mod_access_pb3.conf` 仅可选登记 `DataConfPath`；
- 数据文件经 web monitor **reload 接口热加载**（handler 名 `mod_access_pb3`，照搬 mod_ai_route 模式），Init 时文件缺失按全段缺省容忍（存量部署零配置升级行为不变）；
- 头名称加载时归一为 HTTP 规范化形式：**大小写不敏感**、写入 proto 的 `key` 稳定；多值头按 `,` 拼接；value 截断 2048 字节（对齐 Doris 列宽）；
- **白名单内容不做敏感头限制**（管控归上层配置管理）；原始 API Key 由既有 `maskSensitiveCredentials` 运行时兜底，任何字段不落地。

本场景验证：

- 白名单采集正确性：请求头/响应头写入 `req_headers`/`res_headers`，键为规范化形式，多值拼接；
- 默认行为不变：不配数据文件 / 空白名单时不采集、日志体积零增长；
- 动态配置热加载：修改 `mod_access_pb.data` 调 `/reload/mod_access_pb3` 即时生效；reload 失败（非法内容）保留旧配置；
- 前向兼容：未知段忽略、缺段按缺省；
- 边界：value 2048 截断、原始凭证掩码兜底（红线 #1357）。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程 + 进程内 mock 后端（`common.MockBackend`）。
- 不涉及 `ai-gateway-api`、`conf-agent` 与 Redis（本特性无 Redis 依赖）。
- 通过 `mod_access_pb3` 输出的 b2log 解码 `RequestLog` 断言（复用 SC05 的收集/解码设施）。
- 热加载通过写 `mod_access_pb.data` 后请求 BFE monitor 端口 `/reload/mod_access_pb3` 实现（module 级 WebHandleReload，与 SC46/SC48 的 server-data reload 不同，需新增按路径触发 monitor 接口的辅助函数）。

## 4. 测试 Cluster 与关键配置

### 4.1 cluster_hdr

单 cluster、单 mock 后端即可；`AIConf` 使用最小配置（1 把 Key）。mock 后端 `ResponseFunc` 为响应注入 `X-Trace-Id: trace-<固定值>` 响应头，供白名单采集断言。

### 4.2 mod_access_pb.data 各 TC 形态

| TC | 数据文件形态 |
|----|--------------|
| TC-01/02/07/08 | `{"Version": "...", "access_header": {"req_headers": [...], "res_headers": ["x-trace-id"]}}`（内容见各 TC） |
| TC-03（缺省组） | 不创建文件；对照组：文件存在但 `access_header` 缺失或两列表为空 |
| TC-04 | 初始白名单 A → 热加载改为白名单 B |
| TC-05 | 初始合法文件 → 改写为非法内容（如名称含空格）触发 reload 失败 |
| TC-06 | 含未知顶层段（如 `"sampling": {...}`）与缺 `access_header` 段 |

### 4.3 会话设计

| 客户端 token | key_id | 用途 |
|--------------|--------|------|
| `ak_hdr_a` | `kid-hdr-a` | 主会话（全部 TC） |

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 白名单采集与规范化键 | 请求头/响应头写入 `req_headers`/`res_headers`；proto `key` 为 HTTP 规范化形式（如 `Business_type`）；多值头 `,` 拼接；未命中的头不写条目 |
| TC-02 | 大小写不敏感配置 | 白名单写小写/混合大小写（`business_type`），命中规范化的请求头；同一配置重复大小写变体视为合法但不重复采集 |
| TC-03 | 默认零采集回归（P0 回归） | 不配数据文件（以及文件存在但段缺失/空白名单两个对照）：`req_headers`/`res_headers` 为空、行为与旧版一致 |
| TC-04 | 动态配置热加载 | 改 `mod_access_pb.data` 后调 `/reload/mod_access_pb3`：新白名单即时生效、旧头不再采集，无需重启 |
| TC-05 | reload 失败保留旧配置 | 非法数据文件（非法 JSON / 非法头名）reload 返回错误；旧白名单继续生效、后续请求采集结果不变 |
| TC-06 | 未知段与缺段前向兼容 | 文件含未知顶层段：加载成功、Warn 日志、已知段正常生效；`access_header` 段缺失按空白名单运行 |
| TC-07 | value 2048 截断 | 超长 header 值（>2048 字节）被截断至 2048，行内其余字段完整、导入契约不破 |
| TC-08 | 原始凭证掩码兜底（红线 #1357） | 白名单采集的头值中含原始 API Key（客户端故意构造）时，日志中该值被替换为 `key_id`；`authorization` 独立字段仍恒空 |

## 6. 公共基础设施

1. 复用 SC05 的 b2log 收集/解码设施（`RequestLog` 断言）。
2. 新增 monitor reload 辅助：向 BFE monitor 端口发 `GET /reload/mod_access_pb3`（模块 WebHandleReload handler 名即模块名），返回非 200/含 error 时视为失败——供 TC-04/TC-05 使用。
3. `common/MockBackend`：`ResponseFunc` 注入响应头 `X-Trace-Id`。
4. `common/ProcessEnv`：编译并启动真实 BFE 进程、分配端口（沿用现有设施）。

## 7. 与其他场景的依赖关系

- 依赖 SC05 已验证的 b2log 收集/解码设施与 AI 链路请求构造；
- 依赖 SC39 已验证的 token 鉴权设施（TC-08 的 `key_id` 断言）；
- 凭证掩码红线行为来自 #1357（SC05 已覆盖独立字段，本场景覆盖新增白名单字段）。
