# SC22 AI 意图路由

## 1. 场景背景与目的

`mod_ai_intent` 对 AI 请求做语义意图分类：BFE 对请求调用决策服务（System One 协议 `POST /v1/systemone`）得到意图答案（如 task_type=testing/doc_writing、complexity=simple/medium/complex），路由规则通过新 condition 原语 `req_ai_intent_in(<question>, "<opt1>[|<opt2>...]" [, <min_conf>])` 消费答案，实现语义路由。关键机制：

- **懒解析**：仅当路由规则真的引用意图条件时才触发分类（condition 原语首次求值 → resolver 分类一次 → 结果写入请求上下文），不用意图的流量零开销；
- **读取时置信度门控**：缓存与上下文保存原始概率，unknown 在规则读取答案时按 `intent_questions.data` 当前生效的 `MinConfidence`（全局/逐问题，可热更）派生；规则第三参省略时以该问题的 `MinConfidence` 为门槛，显式门槛（DSL 中显式 0 须写作 `0.0`）为更严格附加门；
- **显式意图头优先**：`X-AI-Intent: <question>=<option>` 合法值直接采信（confidence=1.0，不调决策服务），优先于模型分类；非法条目忽略并回落模型分类；
- **进程内 LRU 缓存**：key 含 questions Version，缓存命中不再调用决策服务；
- **失败永不阻断主请求**：决策服务故障/超时/熔断一律降级为 unknown，意图条件不命中，流量走默认路由，主请求不受影响。

本场景验证：

- 高/中/低置信答案的置信度分层路由与 unknown 兜底（TC-01/02/03）；
- 无对应规则意图（coding）回落默认路由（TC-04）；
- 多问题组合条件（与组合，TC-05）；
- 显式意图头优先与非法显式头忽略（TC-06/07）；
- 决策服务故障降级与熔断打开后的零调用（TC-08/09）；
- 进程内 LRU 缓存命中不再调用决策服务（TC-10）；
- 不用意图原语的路由表对决策服务零调用（懒解析零开销，TC-11）；
- `intent_questions.data` 热加载（bump Version）使已缓存意图失效、新选项在新规则中可用（TC-12）。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程，上游为 mock 后端（`cluster_flash` / `cluster_kimi`），决策服务为 **mock 决策服务**（测试进程内 `httptest.Server`，按"last user message 内容关键词"脚本化返回 System One JSON 响应，并提供调用计数供断言）。
- 不涉及 Redis（意图缓存是进程内 LRU，非 Redis）；不涉及 `ai-gateway-api` 与 `conf-agent`。

## 4. 测试 Cluster 与关键配置

### 4.1 cluster_flash / cluster_kimi

两个 mock 上游后端（复用框架 `common/mock_backend.go`），各返回 200 与固定答案体，答案 content 带 cluster 标识（`cluster_flash` 返回 `from cluster_flash`，`cluster_kimi` 返回 `from cluster_kimi`），响应含 `usage`。`Hits()` 统计命中次数——**"请求落到哪个 cluster"由哪个后端的 `Hits()` 断言**，响应体标识作为辅助佐证。

### 4.2 mock 决策服务

测试进程内 `httptest.Server`，实现 System One 协议 `POST /v1/systemone`：

- **请求**：BFE 组装问题集全量下发（请求体含 `state` 与 `questions`），mock 可读取请求中的问题选项（TC-12 用它判断新版本问题集）；
- **响应脚本**（按 `state` 即 last user message 的关键词匹配，含"设计"的长关键词先于短关键词判定，避免子串误匹配）：

| prompt 关键词 | 响应脚本 |
|---------------|----------|
| 「单元测试」 | `task_type.choice=test_writing`、`probabilities.test_writing=0.93`；若请求 questions 中 task_type 已含 `unit_test` 选项（TC-12 热更后），则改答 `unit_test`、`answer_confidence=0.95` |
| 「测试但复杂」 | `task_type=test_writing`、`answer_confidence=0.72` |
| 「写设计文档」 | `task_type=doc_writing@0.90`；`complexity.score=2`（complex）、`probabilities.complex=0.88` |
| 「写文档」 | `task_type=doc_writing@0.95`；`complexity.score=1`（medium）、`probabilities.medium=0.90` |
| 「重构代码」 | `task_type=coding@0.90` |
| 「很模糊」 | `task_type=test_writing@0.45`（低于全局阈值 0.6 → unknown） |
| 「故障」 | mock 返回 HTTP 500 |
| 其他 | `task_type=coding@0.90`（默认脚本） |

- **System One 响应体样例**（含 `answers.task_type{choice,probabilities}`、`answers.complexity{score,probabilities,legend}` 与 `usage`；score 问题的 `probabilities` 以档位索引为键，BFE 按 Levels 重映射为档位名，`score=1` 即 medium）：

```json
{
    "model": "laya-322m",
    "answers": {
        "task_type": {
            "type": "choice",
            "choice": "test_writing",
            "probabilities": {"coding": 0.02, "test_writing": 0.93, "doc_writing": 0.05},
            "answer_confidence": 0.93
        },
        "complexity": {
            "type": "score",
            "score": 1,
            "probabilities": {"0": 0.05, "1": 0.90, "2": 0.05},
            "legend": ["simple", "medium", "complex"],
            "answer_confidence": 0.90
        }
    },
    "usage": {"prompt_tokens": 12, "completion_tokens": 3}
}
```

- **观测手段**：`Calls()` 记录决策服务被调用次数（每次测试前置清零）；`SetFailAll(bool)` 全局故障开关（打开时任何 prompt 均返回 500，TC-09 用）；模块状态页（monitor 端口 `/monitor/mod_ai_intent`）提供 `ReqTotal/ReqResolved/ReqHeader/ReqCacheHit/ReqUnknown/ReqErr/BreakerOpen/QuestionsVersion` 计数，供辅助断言。
- `mod_ai_intent.conf` 中 `TimeoutMs` 测试值设为 **2000**（本机 CPU 版决策后端延迟高，防止正常分类被误判超时）。

### 4.3 路由表设计

#### apikey_ak_intent（TC-01 ~ TC-10、TC-12 使用）

按序匹配，先命中先生效：

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| intent-flash | `req_ai_intent_in("task_type", "test_writing", 0.9)` | `cluster_flash` | 无 |
| intent-kimi | `req_ai_intent_in("task_type", "test_writing")` | `cluster_kimi` | 无 |
| intent-doc | `req_ai_intent_in("task_type", "doc_writing") && req_ai_intent_in("complexity", "simple\|medium")` | `cluster_flash` | 无 |
| intent-default | `default_t()` | `cluster_kimi` | 无 |

> 说明：规则 1 显式门槛 0.9；规则 2 省略第三参，门槛取 task_type 的 `MinConfidence`（0.6），实现置信度分层；规则 3 为多问题组合条件（与）。DSL 中显式 0 门槛须写作 `0.0`。

#### apikey_ak_plain（TC-11 使用，无意图原语）

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| plain-default | `default_t()` | `cluster_kimi` | 无 |

#### ApikeyRouteTableBindings

```json
{
    "ak_intent": ["apikey_ak_intent"],
    "ak_plain": ["apikey_ak_plain"]
}
```

> 说明：`ak_plain` 用于懒解析零开销测试（TC-11），其路由表不引用任何意图条件。

### 4.4 模块配置与问题集

`mod_ai_intent.conf` 测试值：

```ini
[basic]
DecisionServiceAddr = http://127.0.0.1:<决策服务端口>   # 测试运行时写入 mock 决策服务地址
QuestionsPath = mod_ai_intent/intent_questions.data
TimeoutMs = 2000
MaxStateChars = 2000
CacheSize = 10000
CacheTTLSeconds = 1800
ExplicitIntentHeader = X-AI-Intent

[breaker]
FailureThreshold = 2      # 调低便于 TC-09 快速打开；TC-08 单次故障不足以打开
ProbeIntervalMs = 60000   # 调大避免探测请求在测试窗口内干扰 TC-09 断言
```

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 高置信测试意图分流 | prompt「单元测试」→ test_writing@0.93 → 命中规则1 → cluster_flash；决策服务被调用 1 次（懒解析触发） |
| TC-02 | 中置信测试意图分层 | prompt「测试但复杂」→ 0.72 → 规则1不满足、规则2命中 → cluster_kimi；验证置信度分层 |
| TC-03 | 低置信 unknown 兜底 | prompt「很模糊」→ 0.45<0.6 置 unknown → 规则1/2/3不命中 → 规则4 cluster_kimi；请求本身成功 |
| TC-04 | coding 意图走默认 | prompt「重构代码」→ coding（无 coding 专属规则）→ 规则4 cluster_kimi |
| TC-05 | 多问题组合条件 | prompt「写文档」→ doc+medium → 规则3命中 → cluster_flash；prompt「写设计文档」→ doc+complex → 规则3不命中 → 规则4 cluster_kimi（两次请求） |
| TC-06 | 显式意图头优先 | 带 `X-AI-Intent: task_type=test_writing` 请求（body prompt 为「重构代码」——模型会判 coding）→ 头部采信 → conf=1.0 满足规则1 → cluster_flash；**决策服务调用计数为 0** |
| TC-07 | 非法显式头忽略 | 带 `X-AI-Intent: task_type=bogus`（选项不存在）→ 忽略 → 模型分类（prompt「写文档」→ doc+medium）→ 规则3 cluster_flash |
| TC-08 | 决策服务故障降级 | prompt「故障」（mock 返回 500）→ 全部 unknown → 规则4 cluster_kimi；请求成功；ReqErr 语义 |
| TC-09 | 熔断打开 | 连续触发超过 FailureThreshold 次故障后，即使 mock 恢复可用，后续请求不再调用决策服务（mock 计数停止增长）直接 unknown → cluster_kimi |
| TC-10 | 进程内缓存生效 | 相同 prompt「单元测试」连续请求 2 次 → 决策服务仅被调用 1 次，两次均 cluster_flash（第 2 次 Source=cache） |
| TC-11 | 不用意图的规则零开销 | 绑定到无意图原语路由表（仅 default_t() 规则）的 apikey 发请求 → 决策服务调用计数为 0（懒解析零开销验证） |
| TC-12 | questions 热加载 | 热更新 intent_questions.data（如给 task_type 增删选项并 bump Version）→ 已缓存意图失效：相同 prompt「单元测试」再次请求会重新调用决策服务（计数+1）并按新配置路由；新选项在新规则中可用 |

## 6. 公共基础设施

本场景使用测试框架内置能力，并新增 mock 决策服务：

1. **mock 决策服务（本场景新增，测试进程内 `httptest.Server`）**：按"last user message 内容关键词"脚本化返回 System One JSON 响应（§4.2）；`Calls()` 调用计数供断言；`SetFailAll(bool)` 故障开关（TC-09）；地址运行时写入 `mod_ai_intent.conf` 的 `DecisionServiceAddr`。
2. **`common/mock_backend.go`**：`cluster_flash` / `cluster_kimi` 各挂一个 mock 后端，`Hits()` 统计命中次数，`Body` 为带 cluster 标识的固定答案，用于路由结果断言。
3. **模块状态页与热更接口**：monitor 端口 `/monitor/mod_ai_intent` 的状态计数（`ReqTotal/ReqHeader/ReqCacheHit/ReqUnknown/ReqErr/BreakerOpen/QuestionsVersion`）作辅助断言；TC-12 通过 `/reload/mod_ai_intent?path=` 与 `/reload/mod_ai_route` 触发热更。

> 说明：每个测试例拥有独立临时工作目录、独立 BFE 实例与独立的 mock 计数，用例间无状态泄漏；熔断计数（连续失败）不跨用例累积。

## 7. 与其他场景的依赖关系

- 依赖 SC01 已验证的 `mod_ai_route` 路由表查找与绑定能力；
- 依赖 SC02 已验证的多 API-Key 基础能力（mock 后端 `AIConf.Keys` 注入）；
- 路由结果断言（mock 后端 `Hits()` 计数）复用 SC20 已验证的模式；
- 热加载用例（TC-12）的 `/reload/<module>?path=` 触发方式参考 SC13 已验证的模式。
