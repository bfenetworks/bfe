# TC-04 中止零扣费的行级标记与计数器（issue #1414）

## 用例编号与名称

TC-04 中止零扣费的行级标记与计数器（客户端中断零扣费分支可计数、与"usage 未识别"不再混计；两臂 A1 无 usage / A2 已有初始 usage）

## 所属场景

SC12 客户端中断计费

## 版本声明

- `bfe`：当前源码版本（含 issue #1414 修复：新增计数器 `AbortBillingSkipped` 与 `BillingZeroCost`，`UsageUnrecognized` 语义收窄为"仅上游 usage 未识别"；`ai_usage_source` 新增取值 `aborted` 无需新 proto；`ai_zero_cost_reason` 字段需 `bfe-access-pb >= v0.3.16`）
- 依赖测试设施改造（Phase 6）：SC12 的 `testEnv` 捕获 monitor 端口（`StartBFE` 第二返回值，当前 `sc12_client_abort_billing_test.go` 取的是 `e.bfePort, _, e.stopBFE`），并新增 `mod_ai_token_auth` 计数器读数辅助方法（与 SC03 TC-24 引入的 `tokenAuthMetricsRaw` / `tokenAuthMetric` / `camelToSnake` / `waitForTokenAuthMetric` 同构）

## 测试目的

验证 issue #1414 步骤 5（方案 A + B）落地后的观测性语义：客户端在见到 final usage 之前中断（RST / close / 写失败）时，计费口径**不变**（零扣费，#1352 既定口径，**本用例不主张该形态应计费**），但零扣费不再静默、且与"上游 usage 未识别"可区分：

1. `mod_ai_token_auth.AbortBillingSkipped` 因该分支自增——此前该分支计入 `UsageUnrecognized`，导致"客户端断开"（用户行为，不必告警）污染"usage 未识别"（上游/解析问题，需告警）的告警基线；
2. `UsageUnrecognized` 在该分支**不增**（语义收窄的核心断言）；
3. 请求绑定 RMB 配额计划时 `BillingZeroCost` 自增（零计费收口计数）；
4. 行级标记 `ai_usage_source=aborted` 与 `ai_zero_cost_reason=aborted`（本场景不可断言，见"预期结果"末条与"补充说明"）。

两臂覆盖该分支吸收的两种子形态（同一判定 `aborted && !IsFinalUsageSeen()`）：

| 臂 | 触发 | 断连前已解析的 usage | 修复前可见信号 |
|---|---|---|---|
| A1 | 尚无任何 usage 事件即断连 | 无（token 字段为鉴权期播种残留，`total=0`） | 仅与"上游未识别"混计的 `UsageUnrecognized` |
| A2 | 先投递 `message_start`（`UsedQuota>0`）再断连 | 真实初始 usage（Anthropic `message_start` 不是 final 事件） | 行内 `total>0` 却零成本，**无任何信号**（`ai_cost_value` 缺席、无 `ai_usage_source`） |

## 运行模式

单组件模式：仅启动真实 `bfe` 进程、mock 后端与嵌入式 Redis（同 TC-01/TC-02）；经 monitor 端口读模块计数器。

## 前置条件

1. 已编译 `bfe` 可执行文件（含 issue #1414 修复；`ai_zero_cost_reason` 需 `bfe-access-pb >= v0.3.16`）。
2. BFE 已启动并加载 `cluster_client_abort`，`bfe.conf` 显式设置 `EstimateToken = true`（启用估算，与线上复现场景一致）。
3. Redis（miniredis）已启动，`quota:plan_rmb` 余额预置为 `10000000000`；`ak_user_a` 绑定 RMB 配额计划 `plan_rmb`（`Unit = "RMB"`）。
4. SC12 `bfe.conf` 模板 `MonitorEnabled = true`（默认已满足）；Phase 6 需在 `newTestEnv` 中捕获 monitor 端口并提供计数器读数辅助（`/monitor/mod_ai_token_auth?format=prometheus`，键为 SNAKE_CASE，如 `mod_ai_token_auth_ABORT_BILLING_SKIPPED`）。
5. mock 后端进入 SSE 模式：先发送 `SSEEvents` 并 flush，随后阻塞在 `SSEHold`；`SSETrailing` 在客户端中断后追加一个 1MB `content_block_delta` 帧，强制 BFE 向已关闭的连接写入失败（`ErrClientWrite`，`isClientAbortErr` 覆盖 `ErrClientWrite`/`ErrClientClose`/`ErrClientReset`）。
6. 客户端使用裸 TCP 连接（`http.ReadResponse` 解析 chunked SSE），中断时设置 `SO_LINGER=0` 关闭连接以发送 TCP RST（`abortRST`）。
7. **本场景 `bfe.conf` 未加载 `mod_access_pb3`**，无法解码 b2log（与 SC03 TC-24 的限制相同），故行级字段不作为集成层断言（见"预期结果"末条）。

## 请求构造

两臂相同：

| 字段 | 值 |
|------|-----|
| Method | `POST` |
| Host | `abort-billing.example.org` |
| Path | `/anthropic/v1/messages` |
| Header | `Authorization: Bearer ak_user_a` |
| Header | `anthropic-version: 2023-06-01` |
| Body | `{"model":"claude-opus-4-6","stream":true,"max_tokens":1024}` |

## 后端响应（SSE）

臂 A1（断连时尚无任何 usage；首帧只用于 flush 响应头、不含 usage）：

```
data: {"type":"ping"}

（阻塞于 SSEHold，直至客户端 RST 后释放）

data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"<1MB 填充>"}}
```

臂 A2（先投递 `message_start` 使 `UsedQuota>0`，再断连）：

```
data: {"type":"message_start","message":{"id":"msg_01","type":"message","usage":{"input_tokens":320,"output_tokens":0}}}

（阻塞于 SSEHold，直至客户端 RST 后释放）

data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"<1MB 填充>"}}
```

## 执行步骤

1. 启动 BFE、mock 后端与嵌入式 Redis（捕获 monitor 端口），预置 `quota:plan_rmb = 10000000000`。
2. 臂 A1：设置 `SSEEvents = [{"type":"ping"}]`、`SSEHold = hold1`、`SSETrailing = [1MB content_block_delta]`；客户端发送请求，读到 `ping` 行后 `SO_LINGER=0` RST 中断，随后 `close(hold1)` 释放后端。
3. 轮询 `/monitor/mod_ai_token_auth`（等待请求结束的异步收口），断言 `AbortBillingSkipped == 1`、`BillingZeroCost == 1`、`UsageUnrecognized == 0`；读取 Redis 断言余额 = `10000000000`。
4. 臂 A2：换新 `hold2`，设置 `SSEEvents = [message_start]`、`SSETrailing = [1MB content_block_delta]`；客户端发送请求，读到 `message_start` 行后 RST 中断，随后 `close(hold2)`。
5. 重复步骤 3 的断言，计数为累计值：`AbortBillingSkipped == 2`、`BillingZeroCost == 2`、`UsageUnrecognized == 0`；余额仍为 `10000000000`。
6. 行级字段：本场景无 `mod_access_pb3`，不做 b2log 断言；`ai_usage_source=aborted` / `ai_zero_cost_reason=aborted` 的**判定层**由 `mod_ai_token_auth` 单元测试覆盖，**写日志层**（字段写出/缺席机制）由 `mod_access_pb3` 单元测试覆盖（见"预期结果"末条）。

## 预期结果

- 两臂响应头均为 200（SSE 响应头在断连前已发出，与 TC-01 同）。
- **计费口径不变**：两次请求后 `quota:plan_rmb` 均保持 `10000000000`（零扣费，#1352 既定口径）。**本用例不主张该形态应计费**，只断言其"零扣费且可观测"。
- `AbortBillingSkipped`：臂 A1 后 `1`，臂 A2 后 `2`（该计数器在 abort 分支无条件自增，不要求绑定 RMB 计划）。
- `UsageUnrecognized`：全程 `0`（**核心区分性断言**：客户端中断不再计入"usage 未识别"，该计数器语义自 #1414 起收窄为"仅上游 usage 未识别"）。
- `BillingZeroCost`：臂 A1 后 `1`，臂 A2 后 `2`（abort 分支内以 `hasRMBPlan(ctx.Token.QuotaPlans)` 为条件直接计数——该分支早于通用收口点 `costUnits == 0 && hasRMBPlan(...)`，因此不需要走到计费计算就能计数）。
- **不产生 Warn**：abort 分支自 #1410 起即 counter-only，#1414 明确否决了"为该分支追加 Warn"（方案 C），且收口的 `zeroCostNeedsWarn` 不覆盖 `aborted`——因此本用例无 Warn 可断言，也不存在"Warn 无法做文件断言"的问题（与 SC03 TC-24 §执行步骤 8 的 Warn 限制不同）。
- **行级字段（本场景不可断言）**：
  - `ai_usage_source=aborted`：判定层由单元测试 `TestTokenRequestFinishHandler_ClientAbortCounted` 覆盖（断言 `UsageSource() == aborted`；形态为"无任何 usage 即中止"，对应臂 A1）；写日志层（字段写出/缺席）由 `mod_access_pb3` 的 `TestReqAiInfoGenUsageSource` 覆盖（含"未判定则缺席"与"非 2xx 整组缺席"）；SC05 场景负责访问日志字段口径（SC05 TC-21 覆盖零成本行的 `ai_cost_value` / `ai_zero_cost_reason` 写出与缺席，不含 `aborted` 取值）。
  - `ai_zero_cost_reason=aborted`：判定层同由 `TestTokenRequestFinishHandler_ClientAbortCounted` 覆盖（断言 `ZeroCostReason() == aborted`）；写日志层由 `TestReqAiInfoGenZeroCostReason` 覆盖。
  - **待补覆盖项（诚实边界）**：臂 A2 形态（已有初始 usage、`UsedQuota>0` 后中止）与 A1 由同一判定吸收，但当前单元测试只覆盖 A1 形态（该用例未设置初始 usage）；A2 的**行级标记**在集成层因未加载 `mod_access_pb3` 亦无法断言。本用例在集成层以计数器承载 A2 的信号断言（`AbortBillingSkipped` / `BillingZeroCost` / `UsageUnrecognized`），A2 的行级标记留待 Phase 6 评估补单元测试（`mod_ai_token_auth_test.go` 增 A2 形态用例）或 SC05 补"中止行"臂。

## 补充说明

1. **A2 的已知事实（计费口径问题，另案处理）**：中止分支**整笔跳过扣减，含 token 计划**——`ctx.deducted = true; return`（`bfe_modules/mod_ai_token_auth/mod_ai_token_auth.go:415-422`）位于扣减环（`:533-556`）之前。因此即便 `message_start` 已解析出真实 usage（如 `input_tokens=320`），既不会按初始 usage 计费，也不会扣 token 计划。**"中止时是否应按已解析的初始 usage 计费"属计费口径问题**，issue #1414 明确只做观测、不碰金额，用户已决定另案处理；本用例对此只做记录，不做金额主张。
   - 如需在本场景**端到端证明**该事实，可在臂 A2 额外为 `ak_user_a` 绑定一个 `total_token` 计划（如 `plan_token`，预置 `quota:plan_token`）并断言其余额同样不变。该扩展**待 Phase 6 实施时确认**（需改 `token_rule.data` 生成逻辑）。若保持现状，则该事实仅由代码路径（同一 `return` 早于扣减环）与下面的单元测试限制说明承载：`TestTokenRequestFinishHandler_ClientAbortCounted` 只绑定了 RMB 计划，未覆盖 token 计划的跳过——**本用例不把"token 计划同被跳过"写成已断言的事实**。
2. **臂 A1 的"无 usage"构造**：mock 后端 SSE 模式只有在写出事件时才 flush 响应头（`common/mock_backend.go` 的 `writeSSE` 每次写入后 Flush），因此 A1 需要一个**不含 usage 的首帧**让客户端能观察到 200 响应头并与流同步；A1 的判据是"断连前未见任何 usage 事件"，而非"零个事件"。若 `ping` 帧在 Phase 6 被证明不被 SSE 解析链接受，可改用 `{"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}` —— 两者均无 `usage`，落在同一分支。
3. **与 TC-01/TC-02 的关系**：TC-01（`message_start` 后中断）与 TC-02（final usage 后中断）断言的是**计费结果**（金额），本用例断言的是**观测信号**（计数器）与"与未识别可区分"。计费口径基线由 TC-01/TC-02/TC-03 保持不变，本用例不重复金额断言（仅以余额不变作为"口径未变"的等价断言）。
4. **拆分的原因（修复前状态）**：`UsageUnrecognized` 曾同时承载中止与未识别（#1410 起的该分支计数点，与"上游未识别"守卫共用同一计数器），A2 形态更因 `total>0` 而"看起来像已计费的行"；#1414 起该分支改计 `AbortBillingSkipped` 并置 `ai_usage_source=aborted`。既有 `UsageUnrecognized` 阈值/看板需同步调整（见 `CHANGELOG.md` 的 `Changed` 与 `docs/zh_cn/sys_design/rmb_quota.md` §7.5）。

## 清理

- 停止 BFE、关闭 mock 后端与 Redis，删除临时目录。
