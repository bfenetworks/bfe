# SC10 同 cluster 多 API-Key 会话保持

## 1. 场景背景与目的

当同一个 cluster 下配置多个 Provider API-Key 时，如果同一客户端会话的连续请求被随机分发到不同 Key，会导致 Provider 侧的缓存命中率下降。`bfe` 通过 `AIConf.KeyPolicy.SessionAffinity` 提供基于 `ClientKeyId` 的会话级 Key 亲和性：

- 以 `ClientKeyId`（来自 `mod_ai_token_auth` 的 `key_id`）作为会话标识；
- 在 Redis 中维护 `ClientKeyId -> 选中 Provider Key` 的绑定；
- 当亲和 Key 返回 429/401/403 时，自动轮换并重新绑定；
- 单 Key cluster 直接短路，避免访问 Redis。

本场景验证：

- 开启亲和性时，同一 `ClientKeyId` 的多次请求命中同一 Provider Key；
- 关闭亲和性时，请求按加权随机分发到多个 Key；
- 亲和 Key 返回 429 后，能切换到其他 Key 并更新绑定；
- 单 Key cluster 不生成 Redis 绑定；
- 不同 `ClientKeyId` 有独立绑定；
- BFE 重启后，Redis 绑定仍然保持。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程，并启动内存 Redis 服务（由测试框架提供）。
- 不涉及 `ai-gateway-api` 与 `conf-agent`。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 `EnableAiGateway`，加载 `mod_ai_route`、`mod_ai_token_auth`、`mod_ai_rate_limit` |
| `mod_ai_route/mod_ai_route.conf` | 指定 `ai_route.data` 路径 |
| `mod_ai_route/ai_route.data` | 定义 apikey 级路由规则，命中 `cluster_session_affinity` |
| `mod_ai_token_auth/mod_ai_token_auth.conf` | 指定 token 规则路径 |
| `mod_ai_rate_limit/mod_ai_rate_limit.conf` | 指定限流规则路径，并将 `IsRejectOnRedisError` 设为 `false` |
| `server_data_conf/host_rule.data` | 声明 `ai_product` 产品线对应的 Host |
| `server_data_conf/route_rule.data` | 默认路由 |
| `cluster_conf/gslb.data` | GSLB 权重配置 |
| `cluster_conf/cluster_table.data` | 运行时根据 mock 后端地址动态生成 |
| `cluster_conf/cluster_conf.data` | 运行时根据 mock 后端动态生成，包含 `cluster_session_affinity` 的 `AIConf` 与 `KeyPolicy` |

> 说明：`token_rule.data`、`ai_rate_limit.data` 由测试代码在运行时动态生成，便于控制 token、限流策略与 `AIConf`。

## 4. 测试 Cluster 与 Key 配置

### 4.1 cluster_session_affinity

```json
{
    "AIConf": {
        "Type": 0,
        "Keys": [
            {"Name": "key-a", "Key": "sk-key-a", "Weight": 50},
            {"Name": "key-b", "Key": "sk-key-b", "Weight": 30},
            {"Name": "key-c", "Key": "sk-key-c", "Weight": 20}
        ],
        "KeyPolicy": {
            "Strategy": "weighted_random",
            "MaxRetries": 3,
            "RetryBackoffInitial": 50,
            "RetryBackoffMax": 200,
            "SessionAffinity": true,
            "SessionAffinityTTL": 300,
            "SessionAffinityRedisPrefix": "bfe:ai:key_affinity",
            "SessionAffinityPenaltyEnable": true
        }
    }
}
```

> 说明：TC-02 关闭亲和性时将 `SessionAffinity` 设为 `false`；TC-04 单 Key 场景将 `Keys` 简化为仅 `key-a`。

### 4.2 Redis 绑定键

```
bfe:ai:key_affinity:cluster_session_affinity:<client_key_id>
```

其中 `client_key_id` 来自 `token_rule.data` 中配置的 `key_id`。

### 4.3 路由表设计

#### apikey_ak_session_affinity

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| session-affinity-default | `default_t()` | `cluster_session_affinity` | 无 |

#### ApikeyRouteTableBindings

```json
{
    "ak_session_affinity": ["apikey_ak_session_affinity"],
    "ak_session_affinity_2": ["apikey_ak_session_affinity"]
}
```

> 说明：`ak_session_affinity_2` 用于 TC-05 验证不同 `ClientKeyId` 的独立绑定。

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 开启亲和性时同一 ClientKeyId 命中同一 Key | 50 次请求全部使用同一个 Provider Key |
| TC-02 | 关闭亲和性时请求分散到多个 Key | 200 次请求命中至少 2 个不同 Key |
| TC-03 | 亲和 Key 返回 429 后轮换并重新绑定 | 429 后请求切换到其他 Key，Redis 绑定更新 |
| TC-04 | 单 Key cluster 跳过 Redis 绑定 | 仅配一个 Key 时不读写 Redis 绑定 |
| TC-05 | 不同 ClientKeyId 独立绑定 | 两个 ClientKeyId 各自命中一个 Key，Redis 中存在两条绑定 |
| TC-06 | BFE 重启后绑定保持 | 重启 BFE 后同一 ClientKeyId 仍命中原 Provider Key |
| TC-07 | AIKeyAffinity 未配置时 fail-open | `[AIKeyAffinity]` 禁用时请求正常转发、无 Redis 绑定、Key 随机分发 |

## 5.1 测试例详细说明

### TC-01 开启亲和性时同一 ClientKeyId 命中同一 Key

**目的**：验证开启 `SessionAffinity` 后，同一 `ClientKeyId` 的连续请求被绑定到同一个 Provider Key。

**请求构造**：

| 字段 | 值 |
|------|-----|
| Host | `session-affinity.example.org` |
| Path | `/v1/chat/completions` |
| Header | `Authorization: Bearer ak_session_affinity` |
| Body | `{"model":"gpt-4"}` |

**执行步骤**：

1. 启动 BFE，`SessionAffinity = true`；
2. 使用同一 `ak_session_affinity` 连续发送 50 次请求；
3. 检查 mock 后端收到的 `Authorization` 头。

**预期结果**：

- 50 次请求全部返回 200。
- mock 后端收到的 Provider Key 只有一种（例如 `Bearer sk-key-a`）。

### TC-02 关闭亲和性时请求分散到多个 Key

**目的**：验证 `SessionAffinity = false` 时，请求按加权随机分发，不会绑定到单一 Key。

**执行步骤**：

1. 启动 BFE，`SessionAffinity = false`；
2. 使用同一 `ak_session_affinity` 连续发送 200 次请求；
3. 统计 mock 后端收到的 Provider Key 种类。

**预期结果**：

- 200 次请求全部返回 200。
- mock 后端收到的 Provider Key 种类数 ≥ 2。

### TC-03 亲和 Key 返回 429 后轮换并重新绑定

**目的**：验证亲和 Key 被限流后，BFE 能切换到其他 Key 并更新 Redis 绑定。

**执行步骤**：

1. 启动 BFE，`SessionAffinity = true`；
2. 发送第一次请求，建立 Redis 绑定；
3. 修改 mock 后端逻辑：当请求头为已绑定 Key 时返回 429，否则返回 200；
4. 再发送 20 次请求。

**预期结果**：

- 20 次后续请求全部返回 200。
- 至少有一次请求成功使用了非原绑定 Key。
- Redis 绑定已更新为新的 Provider Key。

### TC-04 单 Key cluster 跳过 Redis 绑定

**目的**：验证 cluster 仅配置一个 Key 时，不生成 Redis 绑定，减少不必要的 Redis 访问。

**执行步骤**：

1. 启动 BFE，`AIConf.Keys` 仅保留 `key-a`；
2. 连续发送 10 次请求；
3. 检查 Redis 中是否存在 `bfe:ai:key_affinity:cluster_session_affinity:session_affinity_key_id`。

**预期结果**：

- 10 次请求全部返回 200，且全部使用 `sk-key-a`。
- Redis 中不存在上述绑定 key。

### TC-05 不同 ClientKeyId 独立绑定

**目的**：验证不同 `ClientKeyId` 有独立的 Key 绑定，互不影响。

**执行步骤**：

1. 启动 BFE，token 表中配置两个 token：`ak_session_affinity`（`key_id = session_affinity_key_id`）和 `ak_session_affinity_2`（`key_id = session_affinity_key_id_2`）；
2. 先用 `ak_session_affinity` 发送 20 次请求；
3. 再用 `ak_session_affinity_2` 发送 20 次请求；
4. 检查 Redis 中两个绑定 key 均存在，并分别统计每组请求使用的 Provider Key。

**预期结果**：

- 两组请求各自只命中一个 Provider Key。
- Redis 中存在 `bfe:ai:key_affinity:cluster_session_affinity:session_affinity_key_id` 与 `...:session_affinity_key_id_2`。

### TC-06 BFE 重启后绑定保持

**目的**：验证 Redis 中的绑定在 BFE 进程重启后仍然有效。

**执行步骤**：

1. 启动 BFE，`SessionAffinity = true`；
2. 发送 10 次请求，记录最终绑定的 Provider Key；
3. 停止 BFE，但保持 mock 后端与 Redis 运行；
4. 使用同一配置重新启动 BFE；
5. 再发送 10 次请求。

**预期结果**：

- 重启后发送的所有请求均使用与重启前相同的 Provider Key。

### TC-07 AIKeyAffinity 未配置时 fail-open

**目的**：验证 `bfe.conf` 未配置 `[AIKeyAffinity]` 段（或 `Disabled = true`）时，即使 cluster 开启 `SessionAffinity`，请求仍正常转发（fail-open），但不建立任何 Redis 绑定。

**执行步骤**：

1. 启动 BFE，`SessionAffinity = true`，且 `[AIKeyAffinity]` 段 `Disabled = true`（等价于未配置，默认即为 `true`）；
2. 使用同一 `ak_session_affinity` 连续发送 50 次请求；
3. 检查响应状态码、Redis 绑定 key 与 mock 后端收到的 Provider Key 种类。

**预期结果**：

- 50 次请求全部返回 200（fail-open 不影响转发）。
- Redis 中不存在绑定 key `bfe:ai:key_affinity:cluster_session_affinity:session_affinity_key_id`。
- mock 后端收到的 Provider Key 至少 2 种（无 affinity，按加权随机分发）。

## 6. 公共基础设施

本场景使用测试框架内置能力：

1. **`common/redis_server.go`**：启动内存 Redis 服务；Key 亲和性逻辑通过 `bfe.conf` 的 `[AIKeyAffinity]` 段（`ServiceConf = redis_bns`，经 `name_conf.data` 解析）由 `bfe_server` 核心自持连接，`mod_ai_rate_limit` 模块使用各自的 `[redis]` 配置连接同一实例。
2. **`common/bfe_config_builder.go`**：根据 `TokenRuleData`、`RateLimitPolicyData` 与 `AIConfs` 动态生成配置文件。
3. **`common/mock_backend.go`**：记录请求头、请求体，并支持按请求动态返回状态码。

## 7. 与其他场景的依赖关系

- 依赖 SC01 已验证的 `mod_ai_route` 路由表查找与绑定能力；
- 依赖 SC02 已验证的多 API-Key 加权选择与 429 轮换能力；
- 依赖 SC07 已验证的 Redis 服务接入能力；
- 不依赖 SC03 / SC09 的 RMB 计费逻辑。
