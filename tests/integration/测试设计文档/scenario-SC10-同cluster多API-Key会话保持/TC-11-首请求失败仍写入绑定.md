# TC-11 首请求失败仍写入绑定

## 用例编号与名称

TC-11 首请求失败仍写入绑定（issue #1472）

## 所属场景

SC10 同 cluster 多 API-Key 会话保持

## 版本声明

- `bfe`：当前源码版本 + issue #1472 修复（未命中路径不再提前 return，转发前的内联 `redisSetBinding` 恢复可达）

## 测试目的

验证会话首触的绑定**不依赖转发成功**：首条请求上游失败时，绑定仍已在选择阶段写入 Redis，因此下一条请求能命中同一 Provider Key，不会因为首请求失败而永远建立不了亲和。

对应设计条款：`multi_api_key.md` §3.5.3 第 4 条（未命中即写入新绑定）与 §3.5.4（重新绑定发生在 Key 失效之后，而非首次选择的先决条件）。

## 运行模式

单组件模式：真实 `bfe` 进程 + 嵌入式 Redis + mock 后端（可切换响应）。

## 前置条件

1. 已编译含 issue #1472 修复的 `bfe` 可执行文件。
2. `[AIKeyAffinity]` 段已启用；cluster 亲和配置同 TC-09（`Keys` 三个、权重 50/30/20、`MaxRetries=3`）。
3. mock 后端可在运行期切换响应（`ResponseFunc`）。

## 配置构造

- 阶段一：mock 后端对所有请求返回 **404**（`{"error":"not found"}`）。
  选 404 的原因：它既不在 cluster fallback 白名单（400/401/402/403/422/429 与 5xx）内，也不触发 Key 轮换或惩罚（429/401/402/403 才触发），因此单次选择、单次上游尝试，客户端直接看到上游错误。
- 阶段二：清空 `ResponseFunc`，恢复默认 200 `{"ok":true}`。

## 执行步骤

1. 启动 BFE 与 Redis（空），把 mock 后端切到阶段一（404）。
2. 发送请求 1，记录响应与 Redis 绑定键。
3. 采样 `ReqAiKeyAffinityMiss`。
4. 把 mock 后端切到阶段二（200）。
5. 发送请求 2，检查 mock 后端最后一次收到的 `Authorization`。

## 预期结果

**请求 1**：

- 响应 **404**（上游错误原样返回，无 fallback 降级）；
- 绑定键 `bfe:ai:key_affinity:cluster_session_affinity:session_affinity_key_id` **已存在**，值为 `key-a`/`key-b`/`key-c` 之一；
- `ReqAiKeyAffinityMiss` = **1**（首触一次未命中）。

**请求 2**：

- 响应 200；
- mock 后端最后一次收到的 `Authorization` 等于请求 1 写入的绑定键对应的 Provider Key 密文（`key-a → sk-key-a` 等），即会话已粘住。

## 清理

停止 `bfe` 进程、Redis 与 mock 后端，删除临时目录。

## 备注

- 修复前的表现：因 `redisGetBinding` 把未命中当错误提前 return，内联写绑定不可达，绑定只能等"转发成功"后由 `aiClusterInvoke` 补写；本用例在修复前会以"绑定键不存在"失败。
- 5xx 不适合本用例：它命中 cluster fallback（`ai_route.data` 默认带 `cluster_session_affinity_fallback`），客户端会看到备用集群的 200，无法区分"首请求失败"。
- 绑定值存的是 Provider Key 的 **Name**（`key-a`），注入上游的 header 是 `Bearer <Key 密文>`（`sk-key-a`），断言时需做一次映射。
