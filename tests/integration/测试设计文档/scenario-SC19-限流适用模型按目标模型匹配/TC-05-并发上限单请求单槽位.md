# TC-05 并发上限单请求单槽位

## 用例编号与名称

TC-05 并发上限单请求单槽位（fallback 不重复预占）

## 所属场景

SC19 限流「适用模型」按目标模型匹配

## 版本声明

- `bfe`：issue #1387 姊妹卡修复起（`targetModelCheckHandler` 幂等守卫：每请求仅检查/预占一次）

## 测试目的

验证最大并发（MaxConcurrency=1）在集群 fallback 路径下不重复占用槽位：回调按 attempt 触发，若无幂等守卫，fallback attempt 会对同一请求二次 `ConnAcquire`（1+1>1），被自身并发槽位误拒（本地 429 `CONCURRENCY_LIMIT_EXCEEDED`）。守卫保证 fallback attempt 跳过检查，请求最终 200；且请求结束后槽位按预占次数正确释放（不泄漏），下一请求不被误拒。

## 运行模式

单组件模式：真实 `bfe` 进程 + 进程内 miniredis（并发计数在共享 Redis）。

## 前置条件

1. `fallback.example.org`：主目标 `cluster_main`（后端始终返回 500）+ fallback `cluster_backup`（后端 200）。
2. 限流策略 `rlp-sc19-con`：`MaxConcurrency=1`，`models=[glm-5.2]`，绑定 `ak_rl`。

## BFE 请求

POST `/v1/chat/completions`，Host `fallback.example.org`，Bearer `ak_rl`，body `{"model":"glm-5.2",...}`，共 2 次（串行）。

## 预期结果

1. 请求 1：主目标 500 → 触发集群 fallback → fallback attempt 由幂等守卫跳过复校 → 最终 200；`cluster_main` 命中 1 次、`cluster_backup` 命中 1 次；
2. 请求 2：同样 5xx → fallback → 200（槽位已正确释放，不泄漏）；`cluster_main` 命中 2 次、`cluster_backup` 命中 2 次。

## 关联

- 修复方案 §2.1（幂等守卫）、§六验收标准 4（计数不膨胀）
