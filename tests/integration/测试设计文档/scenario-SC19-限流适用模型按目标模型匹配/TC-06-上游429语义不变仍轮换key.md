# TC-06 上游 429 语义不变（仍轮换 provider key）

## 用例编号与名称

TC-06 上游 429 语义不变（仍轮换 provider key）

## 所属场景

SC19 限流「适用模型」按目标模型匹配

## 版本声明

- `bfe`：issue #1387 姊妹卡修复起（`ErrCode` 标记区分本地/上游 429；上游 429 行为不变）

## 测试目的

验证守卫只影响本地限流 429、不改变上游 429 语义：`cluster_upstream` 2 个 provider key、`MaxRetries=1`；mock 后端首次命中（任意 key）返回 429，后续命中返回 200。BFE 应把上游 429 归类为「provider key 被限流」并轮换到下一个 key，最终响应 200（区别于 TC-02 的本地 429 不轮换）。

## 运行模式

单组件模式：真实 `bfe` 进程（本 TC 不绑定限流策略，miniredis 仅用于模块接线）。

## 前置条件

1. `cluster_upstream`：2 个 provider key（`upstream-key-1` / `upstream-key-2`），`MaxRetries=1`，无会话亲和。
2. 后端 `ResponseFunc`：第 1 次命中返回 429，其后返回 200 + `usage.total_tokens=15`。
3. token `ak_up`（不绑定限流策略，unlimited 配额）。

## BFE 请求

POST `/v1/chat/completions`，Host `upstream.example.org`，Bearer `ak_up`，body `{"model":"glm-5.2",...}`（1 次）。

## 预期结果

1. 响应 200（首个 key 收到上游 429 后轮换成功）；
2. 后端 Hits = 2；
3. 后端观察到 2 个不同的 provider key Authorization header。
