# TC-21 零成本行显式成本与零成本原因（issue #1414）

## 用例编号与名称

TC-21 零成本行显式成本与零成本原因（已观测 2xx 行显式写出 `ai_cost_value`，零成本行可归因 `ai_zero_cost_reason`，非 2xx 行两者皆缺席）

## 所属场景

SC05 AI 访问日志字段校验

## 版本声明

- `bfe`：当前源码版本（含 issue #1414 修复，见 `docs/zh_cn/modifications/2026-10-13-issue-1414-billing-bypass-observability-gap/design-changes.md`）
- `bfe-access-pb`：`>= v0.3.16`（`ai_zero_cost_reason` 为 field 765；`ai_usage_source` 的 `aborted` 取值无需发版，本用例不涉及 `aborted`）
- 依赖 unit-test 已覆盖的判定层：`TestTokenRequestFinishHandler_AllZeroUsageIsParsed`（全 0 usage → `parsed` + `no_usage_tokens` + `BillingZeroCost` +1，不估算、不扣减）、`TestReqAiInfoGenPriceMiss`（已观测行的 `ai_cost_value=0` 显式写出）、`TestReqAiInfoGenZeroCostReason`（归因字段写出/缺席）、`TestReqAiInfoGenSuppressesUsageOnNon2xx`（非 2xx 整组缺席）

## 测试目的

验证 issue #1414 在访问日志侧的两个收口信号：

1. **零成本与"字段缺席"可区分**：`ai_cost_value` 对**已观测的 2xx 行**总是写出（含 0）——修复前仅在 `UsedCost > 0` 时写出，零成本行与"从未计费"行在日志上同形；
2. **零成本可归因**：绑定 RMB 配额计划而计费为 0 的 2xx 行携带 `ai_zero_cost_reason`，本用例取"上游显式报全 0 usage"这一成因（取值 `no_usage_tokens`）。

三臂设计（对照关系是本用例的核心）：

| 臂 | 形态 | 断言要点 |
|---|---|---|
| 臂 1 | 正常计费的成功请求 | `ai_cost_value > 0`、`ai_zero_cost_reason` **缺席** |
| 臂 2 | 绑定 RMB 计划 + 上游显式返回全 0 usage 的 2xx 请求 | `ai_cost_value = 0`（显式写出）、`ai_usage_source = parsed`、`ai_zero_cost_reason = no_usage_tokens` |
| 臂 3 | 非 2xx（BFE 本地 404，未调用上游） | `ai_cost_value` 与 `ai_zero_cost_reason` **均缺席**（沿用 #1409 / #1414 约定） |

臂 1 与臂 2 构成"同 key、同 cluster、同计费路径，仅上游 usage 不同"的最小对照：一行的 `ai_cost_value` 为正、另一行为显式 0 且有归因，臂 3 则表达"没有可报告的计费结果"。

**臂 2 形态的选择理由（不编造环境能力）**：issue #1414 方案文档允许用"未识别 usage（不可估算）→ `unrecognized`"替代，但本场景**能够稳定构造"全 0 usage"**，故优先采用它——非流式请求的定长 JSON 响应体经 `tokenReadResponseHandler` → `UpdateCtxByUsage` 按 **usage 对象存在性**（`UsagePresent`）识别，全 0 对象同样被写回共享 usage 并 `MarkFinalUsageSeen()`，因此归 `parsed`（不落入 `UsageUnrecognized`、也不被 `EstimateToken` 估算兜底）。这正是 #1414 步骤 1A/1B 的行为，且形成与 SC03 TC-25（同形态、SC03 侧以余额与计数器断言）的跨场景呼应。"未识别 usage"形态在本场景需关闭估算或构造不可整体解析的 chunked 文本响应（见 SC03 TC-24 §前置条件 4），其行级断言已由 SC03 TC-24 覆盖，本用例不重复堆叠。

## 运行模式

单组件模式：仅启动真实 `bfe` 进程与嵌入式 Redis；启用 `mod_access_pb3`，b2log 输出到临时目录，测试结束后解码。

## 前置条件

1. 同 TC-01 的环境（`newTestEnv`）：`cluster_rmb` 命中 `deepseek-chat`（`input_cost_per_token = 1e-6`、`output_cost_per_token = 2e-6`，定点 `100`/`200`），`ak_user_a` 绑定 RMB 配额计划 `plan_rmb`，`quota:plan_rmb` 预置 `10000000000`。
2. `testdata/bfe.conf` 未设置 `Server.EstimateToken`（出厂默认 `true`）——臂 2 的"未被估算"因此是一个真实的反向约束，而不是关闭开关后的平凡结果。
3. `mod_access_pb3` 已加载（SC05 与 SC03 的关键差异：**日志字段断言只在本场景可做**）。
4. 臂 3 复用 TC-19 的"无 AI 路由"构造：`noroute.example.org` 在 `ai_product` 主机列表中，但 `mod_ai_route/ai_route.data` 无对应规则 → token 鉴权先通过（按请求体播种估算值）→ BFE 本地返回 404，未调用任何后端；该臂的响应为 `closeAfterReply`，需用 `sendRequestNoKeepAlive` 逐请求独立连接。
5. mock 后端 `cluster_rmb` 的响应体可在运行期改写（`MockBackend.Body` / `.Response`）。

## BFE 请求

依次发送 3 次 POST 请求（三臂的 Host / 后端响应不同，请求体相同）：

| 臂 | Host | Path | Authorization | 后端响应 | 预期状态码 |
|----|------|------|---------------|----------|------------|
| 臂 1（正常计费） | `rmb.example.org` | `/v1/chat/completions` | `Bearer ak_user_a` | 200 + `{"usage":{"prompt_tokens":100,"completion_tokens":50,"total_tokens":150}}` | 200 |
| 臂 2（全 0 usage） | `rmb.example.org` | `/v1/chat/completions` | `Bearer ak_user_a` | 200 + `{"usage":{"prompt_tokens":0,"completion_tokens":0,"total_tokens":0}}` | 200 |
| 臂 3（非 2xx） | `noroute.example.org` | `/v1/chat/completions` | `Bearer ak_user_a` | 未调用后端 | 404 |

请求体均为 `{"model":"deepseek-chat"}`（与目标模型一致，不触发 body 改写）。

## 预期结果

- 后端命中：臂 1 使 `cluster_rmb` 命中 1 次、臂 2 累计 2 次、臂 3 保持 2 次（臂 3 未调用上游）。
- b2log 中存在 3 条 `RequestLog`，按 `res_status_code`（200/200/404）、`ai_route_rule_hits` 是否为空（臂 3 无路由规则命中）与 `ai_total_tokens`（臂 1 = `150`、臂 2 = `0`；两臂同为 200 且同 Host，需靠该字段或写入顺序区分）区分三臂，逐条断言：
  - 臂 1（`res_status_code=200`，`rmb.example.org`）：`ai_cost_value = 100*100 + 50*200 = 20000`（`> 0`）；`ai_zero_cost_reason` **缺席**（`nil`）；`ai_usage_source = parsed`；`ai_input_tokens = 100`、`ai_output_tokens = 50`、`ai_total_tokens = 150`；
  - 臂 2（`res_status_code=200`，`rmb.example.org`）：`ai_cost_value == 0` 且字段**存在**（`nil` 判定为失败——这是 #1414 "零成本 vs 缺席"的核心断言）；`ai_usage_source = parsed`；`ai_zero_cost_reason = no_usage_tokens`；`ai_input_tokens = 0`、`ai_output_tokens = 0`、`ai_total_tokens = 0`（全 0 usage 被写回共享对象；若估算兜底生效，这些字段会是 `bodyLen/4` 等非 0 值，故它们是"未被估算"的判据）；
  - 臂 3（`res_status_code=404`，`noroute.example.org`）：`ai_cost_value` **缺席**、`ai_zero_cost_reason` **缺席**，且 `ai_input_tokens` / `ai_output_tokens` / `ai_total_tokens` 缺席（复用 TC-19 的 `assertNoUsageFields`）；
  - 公共断言：凭据脱敏（逐条 `assertNoSensitiveCredential`）。
- 计费侧等价断言：臂 2 不产生扣减——`quota:plan_rmb` 余额不变（全 0 usage 按真实 0 计费，未被估算兜底；本用例只把余额作为"未估算/未扣减"的等价证据，具体扣减金额由 SC03 覆盖）。
- **计数器不在本场景断言**：臂 2 的收口点同时使 `mod_ai_token_auth.BillingZeroCost` +1，但 SC05 的 `testEnv` 目前丢弃 monitor 端口（`StartBFE` 第二返回值），本用例不断言计数器；该信号由 SC03 TC-25/TC-26、SC12 TC-04、SC28 TC-11 在各自场景断言（若 Phase 6 在 SC05 捕获 monitor 端口，可顺带断言，属可选强化）。
- **Warn 不做文件断言**：臂 2 的收口点会输出 `RMB plan bound but cost is 0: ... reason=no_usage_tokens`；本场景 `bfe.conf` 无 `[log]` 段、测试框架把 BFE 进程 stdout 直挂测试进程，Warn 无法从文件断言（与 SC03 TC-24 §执行步骤 8 的限制相同），运行日志中人工可见 + 判定层由单元测试覆盖。
- 修复前的形态（用于判断本用例是否真的在验证 #1414）：`ai_zero_cost_reason` 字段尚不存在，臂 2 无论走哪条路都无法表达"上游明确报告 0 用量"——按方案文档 §三 G1 的后果矩阵，全 0 usage 的非流式 2xx 在 `EstimateToken` 默认开启下会保留鉴权期播种值并按 `bodyLen/4` 估算计费（此时 `ai_cost_value` 是非 0 的估算值），或在该形态落零扣费分支时 `ai_cost_value` 缺席且无任何归因字段。

## 清理

停止 `bfe` 进程、mock 后端与嵌入式 Redis，删除临时目录。
