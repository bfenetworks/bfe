# TC-01 默认惩罚时长

## 目的

验证未显式改变配置时，两档惩罚时长取默认值：上游 401/402/403 写 300 秒惩罚键，上游 429 写 60 秒惩罚键。

## 前置条件

- BFE 启动，`cluster_penalty_ttl` 配 2 把 Key（`key-a` / `key-b`，Weight 50/50）；
- `SessionAffinity=true`、`SessionAffinityPenaltyEnable=true`；
- `SessionAffinityPenaltyTTL429=60`、`SessionAffinityPenaltyTTLAuth=300`；
- miniredis 为空（无绑定、无惩罚键）。

## 请求构造

| 字段 | 值 |
|------|-----|
| Method | POST |
| Host | `penalty-ttl.example.org` |
| Path | `/v1/chat/completions` |
| Header | `Authorization: Bearer ak_penalty_ttl`、`Content-Type: application/json` |
| Body | `{"model":"gpt-4"}` |

## 后端响应

| 子用例 | mock 后端行为 |
|--------|----------------|
| 401 档 | 对任意请求返回 `401` + `{"error":"invalid api key"}` |
| 429 档 | 对任意请求返回 `429` + `{"error":"rate limited"}` |

## 执行步骤

1. 启动 BFE（401 档配置）；
2. 发送 1 条请求（Key 级重试会把两把 Key 都试一遍）；
3. 遍历 Redis 中 `bfe:ai:key_affinity:penalty:cluster_penalty_ttl:*` 的键，读取 TTL；
4. 换一套环境（429 档配置），重复 2-3。

## 预期结果

- 429 档：存在 `...:key-a` 与 `...:key-b` 两个惩罚键，TTL 均等于 **60s**（429 走 `usedSet`，轮换一定能把两把 Key 都试到）；
- 401 档：**至少一个**惩罚键，TTL 等于 **300s**。受 §8 记录的既有索引缺陷影响，401 在部分取 Key 顺序下同一请求内只会惩罚一把 Key，因此不对键的数量做严格断言；
- 无 TTL 为 0 的惩罚键（`0` 在 Redis 中表示永不过期）。

## 清理

测试结束时关闭 BFE、mock 后端与 miniredis（`testEnv.Close()`）。
