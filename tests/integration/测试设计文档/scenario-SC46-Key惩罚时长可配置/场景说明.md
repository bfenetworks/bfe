# SC46 Key 惩罚时长可配置

## 1. 场景背景与目的

在 SC10 覆盖的会话级 Key 亲和性里，某把 Provider Key 因上游 429 / 401 / 402 / 403 被判为不可用后，BFE 会在 Redis 写入带过期时间的惩罚键（`{prefix}:penalty:{cluster}:{key_name}`），惩罚窗口内选 Key 会跳过它。惩罚时长原本是代码常量（429 为 60s、401/402/403 为 3600s），2026-10-22 kimi 集群事故（6 次 401 × 3600s，状态存在 Redis、重启不清）中无法调整，只能等过期或人工删键。

issue #1448 把两档惩罚时长改为集群级配置 `AIConf.KeyPolicy.SessionAffinityPenaltyTTL429` / `SessionAffinityPenaltyTTLAuth`（默认 60 / 300 秒），并让「所有 Key 都被惩罚」时合成 429 的 `Retry-After` 与写侧同源。

本场景验证：

- 默认惩罚时长：401 档写 300 秒、429 档写 60 秒；
- 显式配置生效：`SessionAffinityPenaltyTTLAuth=120` / `...TTL429=30` 时惩罚键 TTL 分别为 120 / 30；
- 合成 429 的 `Retry-After` 与 `error.details.retry_after_seconds` 跟随 429 档配置；
- 修改配置并热加载后新惩罚立即使用新时长，无需重启；
- 字段缺省（旧控制面报文，值为 0）归一为默认 60 / 300，不会写出 `expire=0`（永不过期）；
- 单可用 Key 短路：选择时直接返回该 Key，不读惩罚状态、配置的 TTL 无实际效果（与 SC10 TC-04 的前提一致；写侧仍会记录惩罚键，但没有读侧消费）。

对应变更记录：`bfe/docs/zh_cn/modifications/2026-11-04-issue-1448-configurable-key-penalty-ttl/design-changes.md`。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程 + 进程内 miniredis（`common.RedisServer`）。
- 不涉及 `ai-gateway-api` 与 `conf-agent`。
- 通过 miniredis 直接读取惩罚键 TTL，不使用 `PTTL` 接口（BFE 侧尚无该能力）。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 `EnableAiGateway`，加载 `mod_ai_route`、`mod_ai_token_auth`、`mod_ai_rate_limit`，`[AIKeyAffinity]` 指向 miniredis |
| `mod_ai_route/mod_ai_route.conf` + `ai_route.data` | 定义 apikey 级路由，命中 `cluster_penalty_ttl` |
| `mod_ai_token_auth/mod_ai_token_auth.conf` + `token_rule.data` | 定义客户端 token 与稳定 `key_id`（惩罚日志/绑定使用） |
| `mod_ai_rate_limit/mod_ai_rate_limit.conf` + `ai_rate_limit.data` | 放行策略（`rpm` 上限极大），避免限流干扰 |
| `server_data_conf/host_rule.data` | `ai_product` 的 Host 绑定 |
| `server_data_conf/route_rule.data` | 默认路由到 `cluster_penalty_ttl` |
| `cluster_conf/gslb.data` | gslb 权重 |
| `cluster_conf/cluster_table.data` | 运行时按 mock 后端地址生成 |
| `cluster_conf/cluster_conf.data` | 运行时生成，含 `AIConf` 与 `KeyPolicy`（含两个惩罚时长字段） |

## 4. 测试 Cluster 与 Key 配置

### 4.1 cluster_penalty_ttl（默认 2 把 Key）

```json
{
    "AIConf": {
        "Type": 0,
        "Keys": [
            {"Name": "key-a", "Key": "sk-key-a", "Weight": 50},
            {"Name": "key-b", "Key": "sk-key-b", "Weight": 50}
        ],
        "KeyPolicy": {
            "Strategy": "weighted_random",
            "MaxRetries": 3,
            "RetryBackoffInitial": 50,
            "RetryBackoffMax": 200,
            "SessionAffinity": true,
            "SessionAffinityTTL": 300,
            "SessionAffinityRedisPrefix": "bfe:ai:key_affinity",
            "SessionAffinityPenaltyEnable": true,
            "SessionAffinityPenaltyTTL429": 60,
            "SessionAffinityPenaltyTTLAuth": 300
        }
    }
}
```

> 用例差异：TC-02/TC-03 用 `30/120`；TC-04 用 `60/120` 并在热加载后改为 `60/60`；TC-05 只配 `key-a`（Weight 100）；TC-06 两个惩罚字段为 `0`（模拟旧控制面报文）。

### 4.2 Redis 键

```
绑定键：bfe:ai:key_affinity:cluster_penalty_ttl:<key_id>
惩罚键：bfe:ai:key_affinity:penalty:cluster_penalty_ttl:<key_name>
```

### 4.3 路由表设计

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| penalty-ttl-default | `default_t()` | `cluster_penalty_ttl` | 无 |

`ApikeyRouteTableBindings`：`{"ak_penalty_ttl": ["apikey_penalty_ttl"]}`。

> 不配置 fallback cluster：合成 429 直接返回客户端，便于断言 `Retry-After`。

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 默认惩罚时长 | 401 后惩罚键 TTL = 300s；429 后 TTL = 60s |
| TC-02 | 显式配置生效 | `auth=120` → TTL 120s；`429=30` → TTL 30s |
| TC-03 | 合成 429 的 Retry-After 跟随配置 | 两把 Key 都被惩罚后返回 429，`Retry-After: 30`、`details.retry_after_seconds=30`，且零上游交互 |
| TC-04 | 热加载生效 | 改 `cluster_conf.data` 的 auth 档 120 → 60 并 reload，新惩罚 TTL 为 60s，无需重启 |
| TC-05 | 单可用 Key 不参与惩罚过滤 | 只有一把可用 Key 时惩罚过滤被跳过：同 Key 重试 4 次、无绑定键、配置的 TTL 无效果 |
| TC-06 | 缺省值归一 | 两字段为 0（旧控制面）时 401 惩罚 300s、429 惩罚 60s |
| TC-07 | 健康 Key 不被惩罚过滤误跳过 | 绑到 `key-a`、`key-a` 401、`key-b` 200 时，同一请求切到 `key-b` 返回 200（回归下标空间缺陷） |

## 6. 公共基础设施

1. `common/RedisServer`：miniredis 封装；本场景新增 `TTL(key)` 读取剩余 TTL（`ok=false` 表示键不存在），`FastForward` 用于让惩罚键提前过期。
2. `common/BFEConfigBuilder`：按 `AIConfs` 生成 `cluster_conf.data`，按 `TokenRuleData` / `RateLimitPolicyData` 生成模块配置。
3. `common/MockBackend`：`ResponseFunc` 按请求返回 401/429；`Hits()` 统计上游交互次数；`AuthHeaders()` 记录注入的 Provider Key。
4. `common/ProcessEnv`：编译并启动真实 BFE 进程，分配端口。

## 7. 与其他场景的依赖关系

- 依赖 SC10 已验证的 `ClientKeyId` 绑定、`[AIKeyAffinity]` Redis 接入与单 Key 短路语义；
- 依赖 SC02 已验证的 Key 级失败分类（429 轮换 / 401 死亡）；
- 不依赖计费与缓存场景。

## 8. 相关缺陷：惩罚过滤的下标空间错位（已修复）

本场景在实现 #1448 时暴露了一个**与惩罚时长无关的既有缺陷**：`aiKeyAttemptState` 的 `deadSet` / `usedSet` 按 `AIConf.Keys` 下标索引，而 `filterPenaltyKeys` 返回过滤后的子切片、`chooseNextAIKey` 又按子切片下标读写，导致：

- 一把 Key 因 401 被判 dead 且被惩罚过滤掉后，剩下的健康 Key 可能被误判为 dead；
- 同一请求内直接跳到「无可用 Key」的合成 429，健康 Key 未获尝试机会（429 的 `usedSet` 会重置，因此 429 轮换基本不受影响）。

修复方案与实施记录见 `bfe/docs/zh_cn/modifications/2026-11-04-ai-key-penalty-filter-index-mismatch/design-changes.md`：`filterPenaltyKeys` 改为返回原始下标、`chooseNextAIKey` 接收允许下标集合并始终返回 `keys` 空间下标。

本场景的覆盖方式：

- `TC-07` 直接回归该缺陷（绑到 `key-a`、`key-a` 401、`key-b` 200 → 同一请求应返回 200 并命中两次）；
- `TC-01` 的 401 子用例据此恢复为「两个惩罚键」的严格断言。
