# SC20 AI 缓存精确匹配

## 1. 场景背景与目的

`mod_ai_cache` 对符合规则的 AI 请求（OpenAI 协议）做 Redis 精确匹配缓存：请求中的用户问题与历史请求完全一致时，直接返回缓存的答案，不再调用上游模型；缓存命中时跳过配额/费用扣减。本场景为简化版（仅精确匹配，不含语义/向量缓存），验证：

- 首次请求（未命中）正常转发上游，答案被回写到 Redis；
- 相同问题的后续请求命中缓存，不再调用上游，响应标记 `X-Bfe-Ai-Cache: hit`，且可重复命中；
- 不同问题不命中缓存；
- `x-bfe-skip-ai-cache: on` 请求头使当前请求既不读缓存也不写缓存，且不覆盖已有缓存项；
- 流式（SSE）答案按真实分帧 chunk 累积缓存，命中时返回完整 SSE 序列（含 `data:[DONE]`）；
- 租户隔离：不同 API Key 问同一问题互不走缓存；
- TTL 过期后相同问题重新回源；
- 答案超过 `maxValueBytes` 或请求体超过 `maxBodyBytes` 时不缓存；
- 上游响应失败时不写缓存（防缓存污染）；
- 命中缓存时 `mod_ai_token_auth` 跳过 token 配额扣减；
- `allQuestions` 策略下多轮对话历史参与缓存键，尾问相同但历史不同不命中。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程，并启动内存 Redis 服务（由测试框架提供）。
- 不涉及 `ai-gateway-api` 与 `conf-agent`。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 `EnableAiGateway`，加载 `mod_ai_token_auth`、`mod_ai_route`、`mod_ai_cache` |
| `mod_ai_route/mod_ai_route.conf` | 指定 `ai_route.data` 路径 |

| `mod_ai_cache/mod_ai_cache.conf` | 指定缓存规则路径、缓存键前缀、默认 TTL 与 Redis 连接参数 |

| `cluster_conf/gslb.data` | GSLB 权重配置 |

> 说明：`mod_ai_cache_rule.data` 由测试代码在运行时根据 `AiCacheRuleData` 动态生成，便于控制 `cacheKeyStrategy`、`cacheTTL` 与大小限制；Redis 连接通过 `name_conf.data` 将模板中的 BNS 名映射到内存 Redis 地址。

## 4. 测试 Cluster 与缓存配置

### 4.1 cluster_cache

mock 后端 `cluster_cache` 返回 200 与固定答案体：

- 非流式：`{"choices":[{"index":0,"message":{"role":"assistant","content":"BFE is a layer-7 load balancer"},...}],"usage":{"prompt_tokens":10,"completion_tokens":8,"total_tokens":18}}`
- 流式（SSE）：通过 `SSEEvents` 逐帧 flush 3 个 chunk（role-only 首包 + 两段 content：`BFE is` / ` a gateway`），验证跨 chunk 累积

### 4.2 缓存规则

```json
{
    "cond": "default_t()",
    "cacheKeyStrategy": "lastQuestion",
    "cacheTTL": 3600,
    "maxBodyBytes": 1048576,
    "maxValueBytes": 1048576
}
```

缓存键格式：`ai_cache:{key_id}:{question_sha256}`，其中 `key_id` 为 API Key 内部标识（`cache_key_id`），保证租户隔离。

### 4.3 路由表设计

#### apikey_ak_cache / apikey_ak_cache2

| 规则名 | 条件 | targets | fallbacks |
|--------|------|---------|-----------|
| cache-default | `default_t()` | `cluster_cache` | 无 |
| cache-default-2 | `default_t()` | `cluster_cache` | 无 |

#### ApikeyRouteTableBindings

```json
{
    "ak_cache": ["apikey_ak_cache"],
    "ak_cache2": ["apikey_ak_cache2"]
}
```

> 说明：`ak_cache2` 用于租户隔离测试（TC-05），两个 Key 路由到同一 cluster 但具有不同的 `key_id`。

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 精确匹配命中 | 首个请求未命中并回写 Redis；相同问题的第二个请求命中缓存，上游仅被调用 1 次，响应头 `X-Bfe-Ai-Cache: hit`；第三个请求继续命中 |
| TC-02 | 不同问题未命中 | 不同用户问题的请求都到达上游，互不走缓存 |
| TC-03 | 跳过头绕过缓存 | 缓存已存在时，`x-bfe-skip-ai-cache: on` 仍绕过缓存读并到达上游，且不覆盖已有缓存项 |
| TC-04 | 流式缓存命中 | 后端以 SSE 逐帧 flush，答案跨 chunk 累积回写；相同流式请求命中并返回完整 SSE 序列（含 `[DONE]`），上游仅被调用 1 次 |
| TC-05 | 租户隔离 | 两个 API Key 问同一问题互不走缓存（第二个 Key 到达上游），之后各自命中自己的缓存项 |
| TC-06 | TTL 过期 | `cacheTTL=1` 的缓存项过期后（Redis 时钟快进 2s），相同问题重新回源 |
| TC-07 | 答案超限不缓存 | 答案超过 `maxValueBytes` 时不回写，相同问题每次都到达上游 |
| TC-08 | 上游失败不写缓存 | 后端读取部分请求体后断连（无响应），错误响应不回写缓存，重试重新回源 |
| TC-09 | 命中不扣配额 | 有限 `total_token` 配额下，miss 扣减实际 usage（18），hit 不扣减，再次 miss 再扣减 |
| TC-10 | allQuestions 策略 | 多轮对话历史参与缓存键：尾问相同但历史不同不命中，完整对话一致才命中 |
| TC-11 | 请求体超限不缓存 | 请求体超过 `maxBodyBytes` 时不读取缓存键、不回写，每次都到达上游 |

## 6. 公共基础设施

本场景使用测试框架内置能力：

1. **`common/redis_server.go`**：启动内存 Redis 服务，供 `mod_ai_token_auth` 与 `mod_ai_cache` 连接；`FastForward` 用于 TTL 过期测试（TC-06），`SetQuota`/`GetQuota` 用于计费断言（TC-09）。
2. **`common/bfe_config_builder.go`**：根据 `AiCacheRuleData` 动态生成 `mod_ai_cache_rule.data`（测试可覆盖 `cacheKeyStrategy`、`cacheTTL`、`maxBodyBytes`、`maxValueBytes`），并通过 `rewriteModBns("mod_ai_cache")` 将 Redis BNS 映射到内存 Redis。
3. **`common/mock_backend.go`**：`Hits()` 统计上游调用次数；`Body` 可替换为答案；`SSEEvents` 以逐帧 flush 输出 SSE（TC-04）；`ReadBeforeClose` 模拟后端断连（TC-08）。

> 说明：缓存回写发生在 BFE 关闭响应体时，与客户端收到完整响应之间无严格时序保证，测试通过轮询 Redis 键（最长 5s）消除该竞态；配额扣减同样是异步的，通过轮询配额值断言。

## 7. 与其他场景的依赖关系

- 依赖 SC01 已验证的 `mod_ai_route` 路由表查找与绑定能力；
- 依赖 SC02 已验证的多 API-Key 基础能力（mock 后端 `AIConf.Keys` 注入）；
- 计费协同（TC-09）复用 SC11 已验证的配额扣减异步断言模式，覆盖"命中跳过扣减"这一 `mod_ai_cache` 特有行为。
